## 三、核心发现：「无 QTYP」的任务里有真任务

**现行规则**（`gen_quest_table.py`）：「只保留带 QTYP 的任务（玩家可见任务）」。
复盘的第一个筛子 = 「未收录 + **有正式本地化名**」⇒ **1259 条**（内部任务通常没有
本地化名 —— 这个假设被证伪了一半：内部任务也可以有名字）。

第二个筛子 = 排除内部类别关键词（对话/场景/遭遇/指示器/模板/…）⇒ 289 条。

第三个筛子（**关键判据**）= **`subs.QOBJ > 0`（有任务目标子记录）**：
- `QOBJ = 0` 且无 `QTGL` ⇒ 氛围/场景容器（**玩家日志不可见、不是「可接任务」**）——
  例：`City_NA_FAB_Quest01~25`（新亚特兰蒂斯城「住宅/商业区」小事件，共 25+19 条，
  全部 QOBJ=0，**不收**）；
- `QOBJ > 0` ⇒ **完整的玩家任务**（有目标、有 stage 文本、有对话）——
  **289 条候选里只有 20 条**。

### 3.2 为什么不用「QOBJ>0 自动收录」

20 条里 13 条**不该收**（废弃 / 删减 / 主线 / 特质 / 待定）—— 自动规则会误收。
⇒ 落地方式是**人工核验名单**：`ref/extra_quests.json`（每条带 note 证据），
`gen_quest_table.py` 对名单里的任务**豁免「无 QTYP」短路**（itype 由名单给，其它
流程照常：名字 / 过滤 / 三类门槛 / 引导候选）。

## 五、顺带修掉的工具缺陷（本轮）

* **`scan_info_gates.py` 的 op 解析**：旧实现只读 `b[0]`（低字节）—— 实测数据恰好
  都 < 0x100 所以没出错，但不严谨 ⇒ 改 u32 位域（与 `analyze_ctda.py` 一致）。
* **verify 的一处类型错误**：`"…".encode() not in blob`（blob 是 str）会抛 TypeError
  ⇒ verify **静默中断**（后续检查全不跑，且 PowerShell 重定向的输出看起来"正常"）。
  已修 + 提醒：在 str 区不要 `.encode()`；跑 verify 用
  `python tools/esm/_tmp_r106_verify.py` 这类子进程捕获方式避免 PowerShell 管道编码坑。

## 七·方法论沉淀（以后复用）

* 判「任务是不是玩家可见」的**首选信号 = `subs.QOBJ > 0`**（不是名字、不是 QTYP）；
  `QTGL > 0` 是第二信号（有目标位置）。
* 判「玩家能不能接到」：`analyze_start_paths.py`（表内任务的入边）+
  `_tmp_r106_find_starters.py`（任意 EDID 的启动者，含 TIF/终端/对话管理器）。
* 「无脚本启动」≠「接不到」：城市对话管理器（`Dialogue*`）、守卫犯罪脚本、
  终端（TERM_）、故事事件（`SendStoryEvent`）都可以是玩家可达的起点。
* 内部任务的强特征：`MB_`（任务板）/ `SE_` `BE_` `OE_`（事件系统）/
  `Dialogue*`（对话容器）`_Convo_` / `WNPC_`（漫游 NPC）/ `Scene`（场景）/
  `CUT_`（删减）/ `_OLD`（废弃）/ `Patch_`（补丁）/ `SpeechChallenge`（口才挑战子任务）。
