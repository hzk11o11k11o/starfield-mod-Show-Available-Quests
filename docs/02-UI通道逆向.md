## 一、根因 ①：`UI::GetMenuMovie()` 在 1.16.244.0 上查的是错的表

### 1.1 现象

`PushToUI()` 里 `ui->GetMenuMovie(RE::BSFixedString{"BSMissionMenu"})` 返回 null，
所以 `PushToUI()` 在**还没走到 Invoke** 时就 `return false`。

### 1.2 反汇编证据（离线，用 always scan 的 `tools/re/versionlib.py`）

`RE::ID::UI::IsMenuOpen` = **130475** → RVA `0x2544D60`：

```
mov  rbp, rcx                 ; rbp = UI*
...
lea  rcx, [rbp + 0x450]       ; ★ 菜单表 = UI + 0x450
mov  rdx, rsi                 ; const BSFixedString& （菜单名）
lea  r8,  [rsp + 0x20]        ; 输出条目
call 0x142546170              ; 散列表查找
mov  rcx, [rsp + 0x40]        ; = 值 + 0x20
test al, al ; test rcx, rcx ; setne bl   ; 非空 ⇒ 菜单开着
```

commonlibsf 的 `RE/U/UI.h` 把 `menuMap` 标在 **0x470**（还配了 `static_assert`），
中间那个 `unk450[4]`（0x20 字节）被当成"未知"。
**真实情况是：0x470 不是菜单表，0x450 才是。**

查表函数（RVA `0x2546170`）读的字段/算法：

```
mov  rbx, [rcx + 0x40]                  ; 容量（2 的幂）
mov  rsi, [rdx]                         ; key = BSFixedString 里那唯一的 qword（= Entry*）
mov  eax, [rsi + 0x14]                  ; ★ 读 string-pool Entry 的 flags
shr  eax, 1 / test al, 1                ;   kExternal(=1<<1) 位
je   →  lea rcx, [rsi + 0x18]           ;   ✦ 普通条目：字符数据 = Entry + 0x18
jne  →  mov rcx, [rsi + 8]              ;   ✦ 外挂条目：沿 _right 找叶子（函数 0x28CAE80）
mov  rax, rcx / shr rax, 0x20 / xor ecx, eax
                                        ; ★★ 哈希 = charsPtr ^ (charsPtr >> 32)
and  rdx, [rbx - 1]                     ; index = 哈希 & (容量 - 1)
mov  rcx, [rbp + 0x38]                  ; 条目数组指针
imul rax, rdx, 0x38                     ; 条目跨度 0x38
cmp  dword [rax+rcx+0x30], -1           ; nextIndex == -1 ⇒ 空槽
cmp  qword [rax+rcx], rsi               ; ★ key 的**比较**用的是 Entry*（不是 chars）
```

> **这里是两个不同的指针**，混了就必然查不到（第 3 轮的 bug）：
> * `entryKey` = `BSFixedString` 里的 `Entry*` → **只用于比较**；
> * `charsPtr` = 那个 Entry 的**字符数据**（`Entry + 0x18`，外挂条目要沿 `_right` 走到叶子）
>   → **只用于算哈希**。

条目（0x38 字节）与值的布局（`IsMenuOpen` 里 `[rsp+0x40]` 就是值 + 0x20）：

| 位置 | 含义 |
| --- | --- |
| 条目 + 0x00 | key：`BSFixedString` 的 **string-pool 指针**（不是字符串内容！） |
| 条目 + 0x08 | 值本体，0x28 字节 |
| 条目 + 0x30 | nextIndex（`-1` = 空槽） |
| 条目 + 0x34 | index |
| 值 + 0x00 | **`Ptr<IMenu>`** ← 第 5 轮日志实证（`值+0x0->?AVBSMissionMenu@@✔`） |
| 值 + 0x08 / +0x10 / +0x18 | 几个 qword / 1 字节 |
| 值 + 0x20 | `IsMenuOpen` 查它非空的那个字段 |

> commonlibsf 的 `UIMenuEntry` 把 `menu` 标在 +0x00（对应"值 + 0x00"）✓，
> 但它把 `initFunc` 标在 +0x08，与"值 + 0x08 是别的 qword"不一致 —— 所以本 MOD
> 不直接用 `RE::UI::UIMenuMap`，而是按上表自己查，并且**用"对象里存着自己的
> menuName（同一个 string-pool Entry 指针）"来确认拿到的确实是 IMenu**
> （这样完全不需要知道 menuName 在 IMenu 里的偏移）。

## 二、根因 ②：`TESDataHandler::formArrays[FormType::kQUST]` 读到空表

日志里的 `quest 总数=0` 就是这么来的（`formArray` 的 size 读到 0，循环一次没进）。
指针本身是拿到手的（没有 `TESDataHandler 不可用` 的 WARN），所以是 **`formArrays` 的
偏移在这个版本上不对**。离线核对 TESDataHandler 布局成本高、收益低，于是改用另一条更稳的路：
`RE::TESForm::LookupByID`（REL::ID 47401，非 0，实测可用），按静态表里的 FormID
逐个问引擎"这个表单在不在"。

（自检日志 `LogFormArrayProbe` 仍然保留，下次实测顺手记录一下偏移是不是真错。）

## 三、根因 ③：`uiMovie` 抓成了 AS3 的 MovieClip（第 4 轮）

第 4 轮日志（`Documents\My Games\Starfield\SFSE\Logs\SAQ_ShowAvailableQuests.log`）：

```
[21:31:48.415] 推送失败：UI 里没找到 BSMissionMenu 的菜单表条目｜候选表: 0x450(cap=0x200 idx=0x1D0 哈希命中)
                  ｜值内指针: 值+0x8->(无 RTTI)(名字指针不匹配) 值+0x18->(无 RTTI)(名字指针不匹配)
[21:31:48.723] 推送失败：菜单表=UI+0x450 IMenu=值+0x0(.?AVBSMissionMenu@@)
                  uiMovie=IMenu+0x78(.?AVMovieClip@fl_display@Instances@AS3@GFx@Scaleform@@)
                  asMovieRoot=Movie+0x10(弱判据(无RTTI)) Invoke槽=ASMovieRoot+0x3326E10 ★与离线验证值 0x3368DC0 不符
                  Movie(+.?AVMovieClip@...) 里没找到 ASMovieRoot 指针
```

两个有价值的结论：

1. **菜单表命中方式变了**：`48.415` 那次 `值+0x00` 还是空的（菜单实例刚建、还没写进表里），
   400ms 后的 `48.723` 才拿到 `?AVBSMissionMenu@@` —— 所以"失败了要 Retry"这条设计是对的；
2. **`IMenu+0x78` 是 `menuObj` 里的 AS3 对象，不是电影**。为什么 0x78？

`GFx::Value` 的布局（commonlibsf 的 `ScaleformGFxValue.h`，与 GFx SDK 一致）：

| 偏移 | 成员 |
| --- | --- |
| +0x00 | `_prev` |
| +0x08 | `_next` |
| +0x10 | `_objectInterface` |
| +0x18 | `_type` |
| +0x20 | `_value`（联合体，AS3 对象就存在这里） |
| +0x28 | `_dataAux` |

`IMenu::menuObj` 在 **0x58**（commonlibsf 声明），于是 `menuObj._value = 0x58 + 0x20 = 0x78` ——
**0x78 上那个 `?AVMovieClip@fl_display@Instances@AS3@GFx@Scaleform@@` 正好印证了
menuObj 在 0x58、Value 布局如上**（Value 不可能在 0x18 上放对象指针，那是 `_type` 数值）。

> 第 4 轮的错：扫描条件是「RTTI 名字里含 Movie 且不含 MovieDef」，从 0x40 往上一路扫，
> 0x78 比 0x88 先命中 —— 于是抓了个 AS3 的 `MovieClip`（名字里也有 "Movie"）。
> **教训：模糊判据 + 顺序扫描 = 抓错对象。**

### 3.1 这一轮的做法：只认「虚表 RVA」，别再认名字

离线量出来（`tools/re/rtti_slots.py`，全 exe 各只有一个同名类）：

```
.?AVMovieImpl@GFx@Scaleform@@            TD RVA 0x599B150   主 vtable RVA 0x3BCFEE8
.?AVMovieRoot@AS3@GFx@Scaleform@@        TD RVA 0x59A53C0   主 vtable RVA 0x3BE32B0
    [2C]=CreateString  [2D]=CreateStringW  [38]=0x3369180  [39]=0x3368DC0 Invoke  [3A]=0x33691B0 InvokeArgs
```

对象 → `*obj`（虚表）与这两个 RVA 一比，**一次指针比较就能定性，零误判**
（"名字含 Movie"那种判据会被 MovieClip / MovieDef / MovieDefImpl 之类命中）。

### 3.2 解析链（多路径，全部要过硬判据）

```
IMenu（值+0x00，已用 menuName 指针核验）
  ├─ 0x58 menuObj（GFx::Value）
  │    ├─ 0x68 = menuObj._objectInterface
  │    │      ├─ 若它本身就是 AS3::MovieRoot ⇒ 直接用（特例，代码里留着）
  │    │      └─ [+0x08] = MovieImpl*        ← GFx SDK 的 ObjectInterface::movieRoot
  │    └─ 0x78 = menuObj._value（AS3 根对象）：兜底扫描
  └─ 0x88 = uiMovie（commonlibsf 声明）：兜底
  ↓（拿到 MovieImpl 后）
在 MovieImpl 前 0x4000 字节里按「虚表 == 0x3BE32B0」找 ASMovieRoot 指针
  ↓
调用前再核对 vtable[0x39] 的 RVA 必须 == 0x3368DC0，否则**拒绝调用**（Reset 后下次重试）
```

★ 所有"猜偏移"的地方都包在 SEH + `VirtualQuery` 里，猜错最坏是"这次没推送"，
不会把游戏带崩；每种尝试的结果都写进日志。

## 四、语言：判定权交给 AS3（第 5 轮修正）

第 4 轮日志：`菜单打开：静态表=485 引擎里存在=485 待推送=485 语言=en 标题=Available`
—— 游戏明明是中文，`INISettingCollection::GetSetting("sLanguage:General")` 却拿不到值
（而且**本机两个 INI 文件里根本没有 `sLanguage` 这一项**，说明 Steam 版的语言另有来源）。

现在的做法：

* C++ **不再判定语言**（只把读到的值打进日志，标"仅供参考"）；
* 标题与任务名**中英各带一份**一起推给 AS3：`Q\t<FormID>\t<type>\t<中文名>\t<英文名>`；
* AS3 侧用**引擎推来的 `QuestData` 里的任务名**判定语言 —— 那是游戏本地化后的文本，
  最可靠的信号（汉字 ⇒ 中文；拉丁 ⇒ 英文；假名/谚文 ⇒ 不是中文，用英文）。

## 五、SWF 侧：内嵌回退数据（双数据源）

`MissionMenu.as` 里：

```as3
private static const SAQ_EMBEDDED_CHUNKS:Array = [/*__SAQ_EMBEDDED__*/];
```

* 第 1 步构建时 `tools/esm/gen_quest_table.py` 生成
  `ui/missionmenu/saqdata/SaqEmbeddedPayload.inc`（**与 C++ 推送完全同格式的载荷**，
  485 条 ≈ 22.6 K 字符，切成 6 K 一段的字符串字面量）；
* 第 4 步构建时 `tools/build-saq.ps1` 把 `/*__SAQ_EMBEDDED__*/` 替换成这些字面量，
  普通版与 lrg 版各拼一次（lrg 的源码是 `make_lrg_source.py` 从普通版生成的，
  标记会一起带过去）。

于是有两条数据通路，**C++ 推送优先，没有推送就用内嵌表**：

| 通路 | 依赖 | 影响面 |
| --- | --- | --- |
| C++ `Invoke("SetAvailableQuests", 载荷)` | SFSE 插件 + UI 桥全部解析成功 | 以后能做运行时过滤（真实可接状态、跟踪、引导） |
| SWF 内嵌载荷 | 只有 SWF 覆盖生效 | 即使插件没加载/桥没通，"可接任务" tab 也有内容 |

载荷协议（两条通路完全一致）：

```
SAQ1
T\t可接任务\tAvailable
Q\t<FormID>\t<type>\t<中文名>\t<英文名>
```

`SetAvailableQuests` 返回**解析到的条数**（不是过滤后剩下的），C++ 用它判"协议通了"。

## 六、列表条目：字段必须齐全（第 5 轮踩点）

条目对象是直接塞进原版 `MissionsList` 的，UI 各处会读它的字段，少一个就可能
抛 `Error #1010`（实测 `MissionInfo.UpdateMissionInfo` 会读 `param1.sDescription.length`，
所以**没有简介也必须给空串**）。现在给全了：

```as3
{uID, uInstanceID, iType, iFaction, sName, sDescription:"", bActive, bComplete, bFailed,
 bCanBeRejected, bIsMiscQuest, bIsMiscObjective, bCanShowOnMap, iRemainingTime:-1, aObjectives:[]}
```

另外两处配套改动：

* **「全部」tab 的掩码** 从 `0xFFFFFFFF` 改成 `0xFFFFFFBF` —— 去掉
  `1 << AVAILABLE_QUEST_TYPE` 那一位，未接任务只在我们的 tab 里出现，
  不污染原版「全部」列表；
* 条目 `aObjectives: []` 让 `MissionsListEntry.IsMission()` 返回 true（它判的是
  `hasOwnProperty("aObjectives")`），这样条目按"任务"渲染而不是"目标"。
* `iFaction` 用 `FactionUtils.FACTION_NONE`（= -1）⇒ `GetFactionName` 返回空串，
  详情面板不显示派系名（安全）；**但图标不能跟着走 `"None"`**，见第 7.1 节的
  `SaqSafeType` 归一化。

## 七、第 6 轮：列表为空的真根因（可见性判据 + root 路径）

第 5 轮实测现象：**tab 标题正常（「可接任务」），但 tab 里一条都没有**。
两个独立的原因，这一轮都修了。

### 7.1 根因 A：可见性判据用错了字段（界面空白的直接原因）

`MissionsList` 的过滤是：

```as3
// 原版
_loc2_ = param1.iType != null ? (filterMask & 1 << param1.iType) != 0 : true;
```

而我们载荷里的 `iType` 是**任务真实类型**（0=活动 / 2=派系 / 3=杂项 / 4=任务；
没有 1，主线在生成静态表时就被排除了）。「可接任务」tab 的掩码是
`1 << AVAILABLE_QUEST_TYPE`（= `1 << 6` = 64），于是 `64 & (1 << 4)` 之类**恒为 0**
⇒ 485 条全部被滤掉 ⇒ 界面一条不剩。上一轮把「全部」的掩码改成 `0xFFFFFFBF`
（去掉第 6 位）也是同一个误解：我们的条目 `iType` 根本不是 6，那一位没被去掉。

**修法**：`iType` 保留真实类型（图标/类型文本要它），另加一个**专用标记**
`bSaqAvailable: true`，过滤时先看这个标记：

```as3
else if(param1.bSaqAvailable === true)
   _loc2_ = (filterMask & 1 << QuestUtils.AVAILABLE_QUEST_TYPE) != 0;
```

⇒ 带该标记的条目**只**在带 AVAILABLE 位的掩码下可见：出现在我们的 tab、
不出现在「全部」和其它 tab（原先改掩码想达到的效果，现在才真正成立）。

**同时**：`MissionsList.as` 必须**进 patch**（构建脚本此前只同步 `MissionMenu.as`
和 `QuestUtils.as`）—— 补丁不进 SWF，改多少都是白改。`build-saq.ps1` 已同步两个
版本（普通 + lrg）的 `MissionsList.as`。

顺带把 `iType` 归一化（`SaqSafeType`）：原版 `QuestUtils.GetQuestIconLabel` 只对
活动(0)/杂项(3)/任务(4) 返回真实图标帧名，派系(2) 落到 `default -> "None"`，
而 `FactionSymbols` 里未必有 "None" 这一帧 —— `gotoAndStop` 找不到帧会抛异常，
把整行渲染带崩。所以 2 归一成 4（按「任务」图标显示）。

### 7.2 根因 B：C++ 推送 6 条路径全 fail（`Invoke` 的路径从 root 开始）

日志实证：`ASMovieRoot` 已按虚表判据正确拿到（`Invoke槽=0x3368DC0` 与离线值一致），
但 `W/S × SetAvailableQuests / _root.… / _root.root.…` 六种组合全 fail。

原因：**`MissionMenu` 这个类（Embed 自 assets.swf 的 symbol94）是主时间轴上的
子元件，不是 SWF 的 root**。而 `ASMovieRoot::Invoke(path)` 的路径解析**从 root 开始**
—— root 上当然没有这个方法。

**修法**：SWF 侧在 `onAddedToStage` 把入口挂一份到 root（MainTimeline 是 dynamic 的
MovieClip）：

```as3
private function SaqPublishEntryPoint() : void
{
   var _loc1_:Object = this.root;
   if(_loc1_ != null && _loc1_ != this)
      _loc1_["SAQ_SetAvailableQuests"] = this.SetAvailableQuests;  // 方法引用自带 this 绑定
}
```

C++ 侧候选路径把 `SAQ_SetAvailableQuests` / `_root.SAQ_SetAvailableQuests` 放最前
（`SAQ_UI.cpp` 的 `kAttempts`）。

★ 就算 C++ 这一侧还是不通，界面也有内嵌表兜底（两条通路解耦）。

### 7.3 列表掩码的对齐（`SaqSyncListMask`）

`BSScrollingTree` 的默认掩码是 `0xFFFFFFFF`。如果重建列表时还没人设置过掩码，
`bSaqAvailable` 的判据会拿到"全放行"的结果。所以 `SaqRefresh` 重建列表前先把掩码
与当前 tab 对齐一次（越界/未初始化则跳过；切 tab 时仍由 `onFilterChanged` 设置）。

## 八点五、第 8 轮：通道已通（实测），以及一个读取返回值的大坑

### 8.5.1 实测证据（2026-09-19 22:13，三次开菜单全部一致）

```
推送成功：… Invoke槽=ASMovieRoot+0x3368DC0
  探针: SAQ_Probe=fail | _root.SAQ_Probe=6743|SAQ1\nT\t可接任务\tAvailable\nQ\t
  调用: W:SAQ_SetAvailableQuests=fail | W:_root.SAQ_SetAvailableQuests=ok(返回 0)
  载荷=8561 字节/202 条
```

* 探针形状 = `<长度>|<前 24 字符>`，**逐字对得上** ⇒ 载荷完整送达（6743 char vs 8561 字节 UTF-8）。
* 裸名字（不带 `_root.`）的路径一律 fail ⇒ 候选路径应把 `_root.*` 放最前。
* 「返回 0」不是失败，是下面这个 bug。

### 8.5.2 ★ GFx::Value 的**数值必须按类型读**

`GFx::Value` 是联合体：`kInt → _value.int32`（低 4 字节）、`kNumber → _value.number`（8 字节 double）。
`GetNumber()` 就是 `return _value.number;`（release 里连 assert 都没有），于是**把 int 的位模式当 double 解释**：

| AS3 返回 | 类型 | 当成 double 读出来 | `{:.0f}` 打印 | `> 0`? |
| --- | --- | --- | --- | --- |
| 202 | kInt | `1e-321` | `0` | **true** |
| -1 | kInt | `2.12e-314` | `0` | **true** |
| -2 | kInt | `4.24e-314` | `0` | **true** |

⇒ 后果不只是日志难看：`reported > 0` 这个"推送成功"的判据被整数位模式**意外满足**，
连 AS3 明确报的失败码（-1 / -2）都会被记成「推送成功」。
**正确做法**：`IsInt()/IsUInt()/IsNumber()/IsBoolean()` 分别取 `GetInt()/GetUInt()/GetNumber()/GetBoolean()`
（已封装成 `SAQ_UI.cpp::SafeReadValueNumber`，日志里把 -1/-2 翻译成中文说明）。

> 同类教训再记一次：**"ok 但返回值不合理"要先怀疑自己的读取方式**，别急着怀疑对端逻辑。

### 8.5.3 界面状态自证（`SAQ_Report`）

C++ 侧只能证明"我调用了"，证明不了"界面按什么数据在渲染"。于是 AS3 侧加了一个**只读**入口：

```as3
public function SAQ_Report() : String   // src/raw/keep/questData/list/mask/tab/lang/title/visible
```

推送后 C++ 用无参 Invoke 读回来写进日志（`状态:` 段）。判据：

* `src=cpp raw=202 keep≈202−已知 questData=N list=… mask=0x40 tab=7 lang=zh title=可接任务` ⇒ 链路全通；
* `keep=0` ⇒ 已接任务过滤把 202 全滤掉（`QuestData.uID` 语义问题）；
* `mask` ≠ `0x40` 或 `list` 与条目数不符 ⇒ 列表刷新/掩码对齐的问题；
* `SAQ_Report=fail` ⇒ 部署的 SWF 还是旧的。

### 8.5.4 日志卫生

探针/回报读回来的字符串里含 `\n \t`（载荷本身是多行的），原样写日志会把**一行日志劈成三行**
（上一轮日志就是三行拼一行）。现在统一走 `EscapeForLog()` 转成可见的 `\n \t` 并截断。
