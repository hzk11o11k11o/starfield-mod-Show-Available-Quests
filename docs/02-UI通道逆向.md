# 02 · UI 通道逆向（C++ → missionmenu.swf）

> 2026-09-19。起因：第 2 轮游戏内实测 —— 任务菜单里确实多了第 8 个 tab，
> 但**标题显示成原文 token `$SAQ_Avail…`**、**列表一条内容都没有**；
> 插件日志只有一行：`首次菜单打开：quest 总数=0 可接候选=0 推送=失败 (第1次)`。

两条线索都指向同一类问题：**commonlibsf 的声明在游戏 1.16.244.0 上已经过时**。
本文把「怎么查出来的、真实布局是什么、现在代码怎么绕」记下来。

---

## 一、根因 ①：`UI::GetMenuMovie()` 在 1.16.244.0 上查的是错的表

### 1.1 现象

`PushToUI()` 里 `ui->GetMenuMovie(RE::BSFixedString{"BSMissionMenu"})` 返回 null，
所以 `PushToUI()` 在**还没走到 Invoke** 时就 `return false`（这也是日志里
没有 "Invoke 失败" 那条 WARN 的原因 —— 它在更早的分支就返回了）。

### 1.2 反汇编证据（离线，用 always scan 的 `tools/re/versionlib.py`）

`RE::ID::UI::IsMenuOpen` = **130475** → RVA `0x2544D60`：

```
mov  rbp, rcx                 ; rbp = UI*
...
lea  rcx, [rbp + 0x450]       ; ★ 菜单表 = UI + 0x450
mov  rdx, rsi                 ; const BSFixedString& （菜单名）
lea  r8,  [rsp + 0x20]        ; 输出条目
call 0x142546170              ; 散列表查找
mov  rcx, [rsp + 0x40]        ; = 值 + 0x20
test al, al ; test rcx, rcx ; setne bl   ; 非空 ⇒ 菜单开着
```

而 commonlibsf 的 `RE/U/UI.h` 把 `menuMap` 标在 **0x470**（`offsetof` 还配了
`static_assert`），中间那个 `unk450[4]`（0x20 字节）被当成了"未知"。
**真实情况是：0x470 不是菜单表，0x450 才是。**

查表函数（RVA `0x2546170`）读的字段/算法：

```
mov  rbx, [rcx + 0x40]                  ; 容量（2 的幂）
mov  rcx, [rbp + 0x38]                  ; 条目数组指针
imul rax, rdx, 0x38                     ; 条目跨度 0x38
cmp  dword [rax+rcx+0x30], -1           ; nextIndex == -1 ⇒ 空槽
cmp  qword [rax+rcx], rsi               ; key == 查询用的 string-pool 指针（指针比较）
哈希 = keyPtr ^ (keyPtr >> 32)          ; 与 commonlibsf 的 UIMenuNameHash 一致
index = 哈希 & (容量 - 1)               ; 冲突时沿 nextIndex 链走
```

条目（0x38 字节）与值的布局（`IsMenuOpen` 里 `[rsp+0x40]` 就是值 + 0x20）：

| 位置 | 含义 |
| --- | --- |
| 条目 + 0x00 | key：`BSFixedString` 的 **string-pool 指针**（不是字符串内容！） |
| 条目 + 0x08 | 值本体，0x28 字节 |
| 条目 + 0x30 | nextIndex（`-1` = 空槽） |
| 条目 + 0x34 | index |
| 值 + 0x00 | 一个引用计数对象指针（拷贝函数里做了 AddRef/Release） |
| 值 + 0x08 / +0x10 | 两个 qword |
| 值 + 0x18 | 1 字节 |
| 值 + 0x20 | **`Ptr<IMenu>`：菜单实例指针**（`IsMenuOpen` 查它非空） |

> `UIMenuEntry` 在 commonlibsf 里把 `menu` 放在 +0x00、`initFunc` 放在 +0x08，
> 与实测**不一致**，所以本 MOD 不直接用 `RE::UI::UIMenuMap`，而是按上表自己查。

## 二、根因 ②：`TESDataHandler::formArrays[FormType::kQUST]` 读到空表

日志里的 `quest 总数=0` 就是这么来的（`formArray` 的 size 读到 0，循环一次没进）。

- 没有崩、也没有 `TESDataHandler 不可用` 的 WARN ⇒ 指针本身是拿到手的；
- 也就是说 **`formArrays` 的偏移在这个版本上不对**（TESDataHandler 是个巨大的
  POD，成员一动，`0x70` 那个数组就指到别处去了）；
- 离线核对 TESDataHandler 的布局成本高、收益低，所以**改用另一条更稳的路**：
  `RE::TESForm::LookupByID`（REL::ID 47401，非 0，always scan 里实测可用），
  按静态表里的 FormID 逐个问引擎"这个表单在不在"。

代码里另外加了一条**只读长度**的自检日志（`LogFormArrayProbe`），
下次实测就能确认「是不是偏移问题」，为以后可能需要的运行时状态读取铺路：

```
自检: TESDataHandler=0x... formArrays[类型=数量] 61=0 62=0 ...
```

## 三、现在的实现（`plugin/src/SAQ_UI.cpp`）

一次解析、全程缓存，每一层都**自校验**，猜错最坏是「推送失败」而不是崩游戏：

| 层 | 做法 | 校验手段 |
| --- | --- | --- |
| 菜单表 | 先用实测的 `UI+0x450`，不中就在 `0x3C0~0x4C0` 里按 8 字节扫 | 表头形状（容量是 2 的幂且在合理区间）+ 查找必须命中 |
| IMenu | 条目的值里按 `0x20`（实测）→ `0x00/0x08/0x10/0x18` 试 | **对象里存着自己的 `menuName`（同一个 string-pool 指针）** —— 不需要知道它在 IMenu 里的偏移 |
| Movie | `IMenu+0x80~0x140`，判据是 RTTI 名字含 `Movie`（排除 `MovieDef`） | 对象 → 虚表 → `vtable[-1]` = COL → `COL+0x0C` = TypeDescriptor RVA → `TD+0x10` = MSVC 修饰名（实测 `.?AVMovieImpl@GFx@Scaleform@@`） |
| ASMovieRoot | `Movie+0x00~0x40`，判据是 RTTI 名字含 `MovieRoot` | 同上（实测那版是 `.?AVMovieRoot3@GFx@Scaleform@@`） |

RTTI 读不出来时的兜底：退回 commonlibsf 的偏移（`0x88` / `0x10`）+ 「首 qword 落在主模块里」的弱判据，
并在日志里标注 `弱判据(无RTTI)`。

### 3.1 数据协议：一整个字符串（不再用 GFxValue 数组）

旧版要 `CreateArray` / `CreateObject` / `SetMember` / `PushBack` 四个虚函数槽
（槽号一旦和真实 vtable 不一致就会调到别的函数）。现在**只调一个 `Invoke`**，
数据用一段文本传过去，由 AS3 侧自己解析：

```
SAQ1
T\t可接任务
Q\t1122131\t6\t艺术商人
Q\t2409580\t6\t维护和平
...
```

- 字符串用**宽字符 Value**（`kStringW`，GFx 直接按 UTF-16 走，中文不经过任何
  猜测的编码转换）；这一路失败时退回 `CreateString(UTF-8)`。
- 函数路径也按 `SetAvailableQuests` → `_root.SetAvailableQuests` → `_root.root.SetAvailableQuests`
  依次试（不同 Scaleform 版本对「相对路径」的解释不一样）。
- AS3 侧 `SetAvailableQuests` **返回实际拿到的条数**：>0 才算成功
  （0 = 字符串没解析出来，说明编码/传参不对，继续试下一种组合）。
- 每次尝试的结果（编码+路径+返回值）都会写进日志，一轮实测就能定位问题。

### 3.2 虚函数槽的验证（新工具 `tools/re/rtti_slots.py`）

「槽号猜错 = 调到别的函数」是这套做法里最危险的一环，所以离线核对了一遍：

```
python tools/re/rtti_slots.py --td 0x59A53C0 --slots 64 --dis 0x39 --count 45
```

- `Scaleform__GFx__ASMovieRootBase` 的 RTTI（REL::ID 842210）实测 TD =
  `.?AVMovieRoot@AS3@GFx@Scaleform@@`（RVA 0x59A53C0），主 vtable = RVA `0x3BE32B0`；
- 槽 `0x39` = RVA `0x3368DC0`，函数形状与 `Invoke(path, result, args, numArgs)` **完全吻合**：
  `rdx`=路径、`r8`=结果、`r9`=参数数组（步长 **0x30**）、第 5 个参数槽 = numArgs（成员函数的
  第 4 个参数按 Win64 约定走栈）；
- 顺带确认 `commonlibsf` 里 `static_assert(sizeof(Value) == 0x30)` 与实测步长一致。

⇒ commonlibsf 的 **Scaleform** 侧声明（槽号、Value 大小）是可信的；
不可信的是它手工重建的**游戏类**（UI / TESDataHandler）成员偏移 —— 两者要分开对待。

### 3.3 失败重试

菜单刚打开的那一两帧 SWF 可能还没就绪：首轮失败后每 400ms 重试，最多 10 次；
每次"菜单由关变开"都会重新收集并推送一遍。

## 五、下次实测的判据

1. 任务菜单第 8 个 tab 的标题变成 **「可接任务」**（不是 `$SAQ_Avail…`）；
2. 切到该 tab 能看到任务条数与任务名（中文名与游戏语言一致）；
3. 日志里应出现：

```
UI 桥解析：菜单表=UI+0x450 IMenu=值+0x20 uiMovie=IMenu+0x88(.?AVMovieImpl@GFx@Scaleform@@) asMovieRoot=Movie+0x10(.?AVMovieRoot3@GFx@Scaleform@@)
推送成功：... 调用: W:SetAvailableQuests=ok(485) ... 载荷=xxxxx 字节/485 条
菜单打开：静态表=485 引擎里存在=485 推送条数=485 (第1次)
```

4. 若仍失败：按照日志里的 `调用:` 段判断是**路径**问题还是**编码**问题
   （`fail` = 函数没找到；`ok(0)` = 调用到了但字符串没解析出来）。
