# 05 · 任务引导（选中可接任务 → 引擎标记 + 扫描仪路径线）

> 2026-09-19 第 10 轮。对应需求：**「高度整合进游戏原版的任务系统，可以选中跟踪，
> 能调用游戏的任务引导系统正常引导到接取任务的地点（任务目标蓝点，扫描仪任务路径线）」**。

---

## 一、问题：引擎不给「没接的任务」画标记

引擎的画标记判据（BGS 三代一致）：**任务正在运行 + 有一个「已显示」的目标（objective）
+ 那个目标指向某个引用（用别名）**。未接取的任务 `IsRunning == false`
（判据见 `docs/04`），所以它既进不了玩家任务日志，也不会被追踪 —— 没有任何标记。

⇒ 只能**借**：我们自己的 ESM 里放一个「代理任务」，让它带着一个可强制填充的引用别名，
运行时把玩家要去的那个引用塞进去，再把它设为「追踪中」。引擎就会像对待原版任务一样
画出蓝点与路径线。

```
玩家在「可接任务」tab 选中一条 → 按 Enter 或 SET COURSE（键盘 R / 手柄 X）
        │
        ├─ AS3（MissionMenu.as）      SaqGuideSeq++ / SaqGuideQuest = 任务 FormID
        │                             对外暴露 SAQ_PeekGuide() → "<序号>|<FormID>"
        │
        ├─ DLL（SAQ.cpp / SAQ_Guide）  轮询 PeekGuide（100ms）→ 序号变了就是新请求
        │                             按 FormID 在静态表里取「引导目标引用」（下面第二节）
        │                             写 GLOB：SAQ_GuideTargetRef = 目标引用
        │                                       SAQ_GuideState    = 0（=有新请求）
        │
        ├─ Papyrus（SAQ_Main.psc）     0.5s 轮询（StartTimer/OnTimer，Starfield 没有
        │                             RegisterForUpdate）+ 菜单关闭时立刻检查
        │                             GuideState == 0 ⇒ 干活：
        │                               GetAlias(0).ForceRefTo(目标)
        │                               SetObjectiveDisplayed(10, true, true)
        │                               SetActive(true)      ← 引擎开始「追踪」这条代理任务
        │                             然后 GuideState = 1（已应用）/ 2（目标取不到）/ 4（别名不存在）
        │
        └─ 引擎                        目标别名已填充 + 目标已显示 + 任务被追踪
                                       ⇒ 任务标记（蓝点）+ 扫描仪路径线
```

代理任务与别名（`SAQ_MainQuest`）：目标 10 的显示文本是 `<Alias=SAQ_GuideTarget>` ——
引擎会把别名里那个引用的**本地化名字**填进去（中英随游戏语言），所以 HUD 上显示的是
「文森特·萨利纳斯」这样的目标名，而不是一句写死的文案。

## 二、「去哪里接」这个引用怎么算出来（离线数据）

`tools/esm/gen_guide_targets.py`（第 17 轮起：遍历**全部 master**（基础游戏 + 各 DLC），
约 3-6 分钟）。

> **多 master（第 17 轮）**：别名数据改成**直接解析 ESM**（`ALST/ALID/ALUA/ALFR/ALFL`），
> 不再依赖 xEdit 的树状导出；每条目标记 `refrMaster`（记录号 + 所属插件）——
> 一条 DLC 任务引用的 NPC / 地点可能在基础游戏里，反之亦然。
> 运行期由 `SAQ_Masters::MakeFormID()` 按加载顺序拼出真正的 FormID。

| 优先级 | 来源 | 说明 | 覆盖（202 条候选） |
| --- | --- | --- | --- |
| 1 | **ALFR「Forced Reference」** | 任务记录里自己写的一个具体引用（`XMarker`/`EnableRef`/地标 `MapMarker` 之类），**通常是常驻引用**；落在「别名暂存格」里的丢掉 | 64 条 |
| 2 | **ALUA「Unique Actor」→ 该 NPC 的放置引用（ACHR）** | 任务发布者；标记会跟着人走 | 104 条 |
| 3 | QUST `LNAM` / ALFL「Specific Location」→ LCTN `MNAM` | 任务地点的**地图标记引用**（只有少部分地点有） | 0 条（能被上面的吃掉） |
| — | 合计 | | **168 / 202 = 83%** |

排序键（`collect_candidates`）：**先「常驻（persistent）」**（即记录标志 `0x400` —— 格子没
加载时 `Game.GetForm` 也拿得到、`ForceRefTo` 也能成；临时引用要等格子加载），
再按来源质量（发布者 > 任务落脚点 > 地点标记）、是否杂兵名（Guard/Settler/…）、出现顺序。

实测：168 条里 **常驻 100 条**、非常驻 68 条（都是「发布者只有临时放置」的情况）。

### 关键数据证据（都可复现）

* `QUST.LNAM` = 任务的 Location（LCTN FormID）。
* `LCTN.MNAM` = 该地点的**地图标记引用**：
  `CityNewAtlantisLodgeLocation`(LCTN 0027C8ED)`.MNAM` = `000F93F1`
  = `NewAtlantisMapMarkerLodge`（`XMRK` 地图标记 + `FULL` 名字「陋室」）。
* NPC 放置引用：全表遍历 CELL/WRLD 组，找 `NAME == NPC_` 的 ACHR。
  `FC_Neon_HuongLe`(NPC_ 0005797C) → ACHR 0005797D `Neon_HuongRef`（cell 00294F32 / world 0027CF9E NeonCity）。
* xEdit 导出里的别名形态（`ref/xedit/quests_typed.txt`）：
  `ALUA - Unique Actor = FC_Neon_HuongLe "Huong Le" [NPC_:0005797C]`；
  `ALFR - Forced Reference = FFNeonZ09_EnableRef [REFR:00089760] (places XMarker … in NeonCity "Neon")`。

排除项（BAD_CELL_RE）：别名暂存格（`…AliasCell` / `DO NOT DELETE` / `Holding`）里的引用
一律不用 —— 玩家到不了那里，标记会指向空气（例：`CF01_InviteSlateRef` 在
`CrimsonFleetAliasCell "CF Alias Cell - DO NOT DELETE"` 里）。

## 三、ESM 补丁（`tools/esm/patch_saq_esm.py`）

代理任务原来是 xEdit 生成的一个「空壳」QUST（只有 EDID/VMAD/DNAM）。引导需要它带
**一个引用别名 + 一个目标指向该别名**，这两样由本补丁直接写字节完成（幂等，可反复跑，
`build-saq.ps1` 的 ESM 步骤之后会自动执行）。

记录结构（**格式全部从 Starfield.esm 里的真实样板抄来**，不是猜的）：

```
Reference Alias（脚本填充型，样板 SQ_Followers\AvailableFollowers）
  ALST(4)=别名id | ALID(N)=名字+NUL | FNAM(4)=标志 | ALFG(4) | VTCK(4) | ALED(0)
Objective（样板 MB_Bounty01Far 的目标）
  QOBJ(2)=目标索引 | FNAM(4)=标志 | NNAM(文本) | QSTA(12)=别名id|标志|关键词
ANAM(4) = 下一个空闲别名 id
```

本 MOD 写进去的内容：

```
QOBJ=10 | FNAM=0 | NNAM="<Alias=SAQ_GuideTarget>" | QSTA={alias 0,0,0}
ANAM=1
ALST=0 | ALID="SAQ_GuideTarget" | FNAM=0x02 | ALFG=0 | VTCK=0 | ALED
```

* 文本用**内联字符串**：本文件的 TES4 头 flags = `0x01`（**没有** `0x80` = Localized），
  所以文本字段是内联的，**不需要**往游戏的 strings/`Localization.ba2` 里加 ID。
* 别名不给任何填充方式（脚本填充型的标准做法）⇒ 任务启动时它保持空，`ForceRefTo` 可用；
  也不会因为「别名填不上」把 Start Game Enabled 的任务卡在启动阶段。
* 别名标志取 `0x02`，与同样是「脚本运行时填充」的 `AvailableFollowers` 一致。
* 自校验：写完重新解析一遍，并检查「每条记录都正好填满自己所属的 GRUP」。

### 坑（踩过一次）

`write_esm` 原来用「原组大小 + 增量」修 GRUP 的 size，结果第一次写坏之后错误被继承下去，
记录越过了组的边界。现在改成**整体重新序列化 + 重算组大小**，并用
`walk_linear()`（不依赖 GRUP size 的线性遍历）读文件 —— 对残留错误免疫。

## 四、DLL ↔ Papyrus 的通道（GLOB）

SFSE 的接口只有 `QueryInterface / Messaging / Trampoline / Menu / Task` —— **没有** SKSE
那种「C++ 直接给 Papyrus 发 ModCallbackEvent」的通道。所以 DLL→Papyrus 只能借引擎自己
认得的持久对象：**GLOB**（一个 float）。

| GLOB | 记录号 | 方向 | 含义 |
| --- | --- | --- | --- |
| `SAQ_GuideTargetRef` | 0x801 | DLL → 脚本 | 引导目标 FormID 的**低 24 位**（0 = 取消引导） |
| `SAQ_GuideState` | 0x802 | 脚本 → DLL | 0 待处理 / 1 已应用 / 2 目标取不到 / 3 已清除 / 4 别名不存在 |
| `SAQ_Notify` | 0x803 | 脚本 → DLL | **7777 + 菜单打开次数**（身份锚点 + 证据链） |
| `SAQ_TestMode` | 0x804 | 玩家 → DLL | 测试过滤开关（ini / 控制台，见第八节） |
| `SAQ_GuidePrefix` | 0x805 | DLL → 脚本 | 引导目标 FormID 的**高 8 位**（第 21 轮，见下） |

新增记录一律**追加在末尾**（FormID 存进存档，老的不能挪）。

### ★ 怎么找到自己的 GLOB（本模块最容易踩的地方）

FormID = `(加载顺序序号 << 24) | 记录号`，而**序号运行期才知道**（MO2 顺序、DLC 都会影响），
所以不能把 `0x02000801` 写死。做法是让脚本给一个身份锚点：

* `SAQ_Main.psc` 在 `OnInit` 里把 `SAQ_Notify` 写成 `7777`，之后每次菜单打开 +1；
* DLL 遍历 `0x00..0xFF` 个前缀，在 `0x803` 上找「值落在 7777..8776 的 GLOB」= 自己的插件；
  再取同前缀的 `0x801/0x802`。

这一步顺带把整条证据链补齐了：

| 日志里看到 | 结论 |
| --- | --- |
| `ESM 通道：前缀=0xNN 目标=… 状态=… 通知=7777` | ESM 已加载、代理任务在跑、**脚本活着**、GLOB 读写通 |
| `通知` 的值在涨 | 脚本看得到任务菜单的开关事件 |
| `ESM 通道：未认领（…候选: 0x02:0 …）` | ESM 没启用 / 脚本没跑 / 记录号变了（候选里能看到各前缀读到的原始值） |

写之前还有一道自检（`SetGuideTarget`）：`GuideState` 必须落在 `[-0.5, 8]`，
目标分量必须看起来像 FormID —— 认领靠读 `TESGlobal::value`，这一步等于再确认一次
「偏移在本机是对的」，不对就拒绝写内存。

### ★★ GLOB 是 float：完整 FormID 存不下（第 21 轮实机 bug）

**症状**（2026-09-20 实测日志）：引导过一次 DLC 任务后（目标 `0x0107BDB2`「瓦鲁贮藏所」），
**之后每次写入都被拒绝**（结果码 2）——玩家看到「点亮瞬间就取消、其余条目全部点不亮」：

```
[10:24:11.501] 引导请求：同情生者（0x010D5E84）→ 引用 0x0107BDB2（瓦鲁贮藏所）   ← 写入成功
[10:24:11.940] [W] 引导请求：取消失败｜拒绝写入：SAQ_GuideTargetRef 读出来是 17284530（不像 FormID）
```

两个叠加的错：

| # | 错 | 后果 |
| --- | --- | --- |
| 1 | 自检上限写成 `0xFFFFFF`（那是**低 24 位**的上限），而 `target` 里存的是**完整 FormID** | DLC 目标的完整 FormID 会超过它 ⇒ 通道里存过这种值后**每次写入都被拒** |
| 2 | GLOB 是 float（尾数 24 位），完整 FormID > 2^24 后**奇数不能精确表示**（±1） | 轻则 `GetForm` 取不到（状态 2），重则**指向相邻的另一条记录 = 错误的引导目标** |

**修法**：目标的完整 FormID 拆成两个 GLOB —— 低 24 位（`0x801`）+ 高 8 位（`0x805`），
两个分量都在 float 精确区内；脚本按 `GuidePrefix 是否存在` 自动兼容旧通道；
自检改成分量检查，并保留对「修复前残留的完整值」的兼容（会被下一次写入覆盖，不会卡死）。

> 教训：**凡是走 float 通道传数值，先问一句「这个值的量级会不会超过 2^24」**。
> （`TESGlobal::value` 的偏移是 `0x48` —— commonlibsf 头文件里有 static_assert，
> 上一代项目修正过；原头文件写 0x40 是错的。）

## 五、Papyrus 侧（`scripts/SAQ_Main.psc`）

* `OnInit`：写身份锚点、`RegisterForMenuOpenCloseEvent("BSMissionMenu")`、`StartTimer(0.5, 1)`。
* `OnTimer`：重新排下一拍 + `ApplyGuide()`。
  （Starfield 的 Papyrus **没有** `RegisterForUpdate`，只有一次性 `StartTimer`，
  所以要自己重排；0.5 秒一次的空判开销可忽略。）
* `OnMenuOpenCloseEvent`：开 → `SAQ_Notify += 1` + `Debug.Trace("[SAQ] 菜单打开 通知=N")`
  （★ 第 19 轮：这行 Trace 是「脚本活性」的直接证据，DLL 侧有对应的活性探测，见六·补三）；
  关 → 立刻 `ApplyGuide()`（不用等下一拍）。
* `ApplyGuide()`：`GuideState != 0` 直接返回；否则按目标 FormID `Game.GetForm(...) as ObjectReference`
  → `ForceRefTo` + `SetObjectiveDisplayed(10, true, true)` + `SetActive(true)`。
* 别名用 **`GetAlias(0)`** 取，而不是写 VMAD「别名属性」—— 后者要自己拼 Object/Alias
  联合体的字节，容易错；`GetAlias(int)` 是原生函数，零风险。
* `AutoConst` 在 Starfield 的 Papyrus 4.7 里**不存在**（实测报 `Unknown user flag autoconst`），
  常量属性要写 `AutoReadOnly`。
* ★ 第 26 轮：**每个「菜单打开」事件都重挂一次 `StartTimer` 并补一次 `ApplyGuide()`**。
  原因（实测）：脚本实例**从存档恢复时 `OnInit` 不跑**（三个会话的 Papyrus 日志里都没有
  `OnInit`），而 `StartTimer` 不随存档恢复 ⇒ 定时器从来没注册过 ⇒ 菜单开着时脚本没有任何
  轮询机会，引导只能靠「菜单关闭」分支里的 `ApplyGuide()` 应用一次。
  `StartTimer` 重复调用同一 id 只是重置，无副作用。

## 六、AS3 侧（`ui/missionmenu/src/MissionMenu.as`）

* 「可接任务」条目（`bSaqAvailable`）在原版里 `CanTrackOrUntrack == false`（引擎不认它），
  所以在 `onMissionListItemActivated`（Enter）与 `OnPlotCourseEvent`（SET COURSE：键盘 R / 手柄 X）里
  **先于原版判定**拦下来 → `SaqToggleGuide()`。
* `onMissionSelectionChange`：选中我们的条目时把 SET COURSE 按钮置为可用
  （「显示在地图上」保持禁用 —— 引擎里没有这条任务的位置数据）。
* ★ **提示里的键名不要写死**（第 15 轮踩过）：`SET COURSE` 的 `UserEventData` 事件名是
  `"XButton"`，那是**手柄 X 按钮**的内部名；键盘下同一事件映射到 **R**。文案里的键名要用
  `KeyHelper.GetButtonNameForEvent("XButton","")` 动态取（与底部按钮栏同一来源），
  取不到就退回「使用底部的设定航线按钮」，否则会提示出游戏里不存在的「X 键」。
* `SAQ_PeekGuide()` 暴露 `"<序号>|<任务FormID>"`；DLL 每 100ms 读一次，序号变才处理
  （同一条再按一次 = 取消，FormID 传 0）。
* `SAQ_Report` 尾部加 `guide=<序号>|<FormID>|<最后一次动作>`，日志里能看到玩家点了什么。
* ★ 第 23 轮：**「能不能导航」要看得见**。载荷第 5 列 = `hasGuideTarget`（1/0，来自静态表
  `guideRefLocal`），界面据此：
  * 无目标的条目（261 条里 52 条）：右侧描述直接写明「还没有导航目标」、
    SET COURSE 按钮**置灰**、点击**不发请求**（此前是「亮起 → 结果码 1 → 瞬间回滚」，
    玩家看不出原因，实测以为坏了）；
  * 有目标：照旧（点了就发引导请求）。
  内嵌回退数据的生成器（`gen_quest_table.py::build_payload`）同步加了这一列。

### 六·补、界面状态与「真实引导」的同步（第 16 轮）

AS3 的 `SaqToggleGuide` 只能在**本地立刻**切状态（音效 / 竖条 / 文案），但「这条任务
到底有没有引导目标」「现在实际在引导哪条」只有 DLL 知道。缺回写通道时踩过两个坑
（都有日志实证）：

| 现象（日志） | 根因 | 修复 |
| --- | --- | --- |
| 点「调查结果」→ 界面 `guide=…已设为引导:调查结果`，DLL 却打 `引导请求：…没有引导目标` | DLL 拒绝时只写日志、不回传；界面停在「已设为引导」，实际什么都没变（旧引导还在时更误导） | DLL 回写 `_root.SAQ_GuideReply("<seq>\|<实际FormID>\|<结果码>")`；AS3 按「实际值」对齐：不一致 = 被拒绝 → 回滚竖条 + OFF 音 + 失败文案 |
| 菜单重开后界面 `guide=0\|0\|-`，DLL 还在引导「群众心态」 | 菜单每次打开是新 SWF 实例，`SaqGuideQuest` 归 0 ⇒ ① 竖条丢失 ② 点「正在引导的那条」第一次变成重设而非取消 | 推送成功后 DLL 调 `_root.SAQ_SyncGuideState("<实际FormID>")`；AS3 只在玩家没操作过（`SaqGuideSeq == 0`）时接受 |

结果码约定（DLL → AS3）：`0=成功 / 1=没有引导目标 / 2=写 ESM 通道失败 / 3=静态表里没有这条`
/ ★ 第 19 轮新增 `4=引导未生效（脚本确认超时 / 别名不存在）` —— 界面回滚，见六·补三。
应答（AS3 → DLL，只进日志）：`ok / same / stale（玩家已点了新的，原请求作废）/ skip / bad`。

### 六·补二、第 17 轮：引导链路的三处「沉默」被补上（都有日志实证）

| 沉默 | 现象（第 16 轮日志） | 修法 |
| --- | --- | --- |
| **下发结果没人确认** | 09:18:39 下发成功 → 09:18:46 关菜单，日志里没有一行说明脚本有没有应用 | DLL `PollGuideVerify`：下发后 900ms 起轮询 `SAQ_GuideState` —— `1` 记 `引导已生效：…`；`2/3` 自动重发（≤2 次）；`4` 明确报「别名不存在」；一直 `0` 则超时 WARN。菜单关掉后也继续跑（脚本正是在关菜单时应用引导） |
| **重启/读档后不认领已有引导** | 引导状态存在 GLOB 里（跟着存档走），DLL 内存是空的 ⇒ 日志 `引导状态：无`，而游戏里还挂着旧蓝点，且没有任何入口能取消它 | DLL `AdoptExistingGuide`：开菜单时若「自认为没在引导」而通道里有目标 ⇒ 按目标引用反查静态表认领回来（`认领已有引导：…`），UI 随即同步成「正在引导」 |
| **接到任务后引导不消失** | 只有「已完成」会自动取消；玩家接到手之后 HUD 还一直指着那个地点 | AS3 `SaqAutoCancelIfAccepted`：`SaqRefresh` 里发现被引导的 uID 出现在玩家任务日志（QuestData）⇒ 序号 +1、目标清 0（与手动取消同一条路）；DLL 侧**不需要新协议** |

**另外两处「静默失效」的自愈**（同轮）：

* **脚本重挂**：读档会让 `SAQ_Main` 重新 `OnInit`（一次会话实测 3 次）——别名被清空、
  脚本把 `GuideState` 写成 3，而 DLL/界面仍认为在引导（蓝点其实没了）。
  → 脚本 `OnInit` 里发现 `GuideTargetRef > 0` 就把 `GuideState` 置回 0（轮询会重新应用）。
* **引用当时没加载**（脚本状态 = 2）：非常驻引用在远处取不到，之后玩家飞近了脚本
  也不会自己重试。→ DLL 在每次打开菜单时检查，发现「自己认为在引导 + 状态是 2/3」
  就重写一遍通道（`引导重新下发：…`）。状态 4（别名不存在）不重发 —— ESM 补丁没生效，重发没用。

### 六·补三、第 19 轮：脚本活性探测 + 「引导未生效」的收尾

**起因**（第 18 轮实测日志复查）：该会话的 Papyrus 日志（09:54~09:56，749 行活跃）
里**没有任何 SAQ_Main 痕迹**（历史会话每次都有 `SAQ_Main OnInit`），而 DLL 读到的
`通知=7778` 与上一次会话完全相同 —— 无法区分「脚本实例从存档恢复后僵死（收不到
菜单事件/定时器）」和「DLL 读通道比脚本处理早」。若真僵死，玩家点引导会
「写入成功但没人处理」：界面显示已引导，世界里什么都没有。

| 改动 | 说明 |
| --- | --- |
| 脚本 Trace（`SAQ_Main.psc`） | 开菜单时 `Debug.Trace("[SAQ] 菜单打开 通知=N")` —— Papyrus 日志从此可**直接证明**脚本在响应菜单事件 |
| DLL 活性探测（`SAQ.cpp::CheckScriptLiveness`） | 开菜单 1.5 秒后复读 `SAQ_Notify`：值 +1 ⇒ 脚本活着（静默）；没涨 ⇒ WARN 留证（每轮菜单一次） |
| 「引导未生效」收尾（`AbortUnverifiedGuide`） | `PollGuideVerify` 确认超时（≈11 秒状态仍是 0）或状态 4（别名不存在）时：清 ESM 通道 + 清本侧状态 +（菜单开着时）用**结果码 4** 回写界面回滚。否则界面会一直显示「正在引导」（界面说谎），且下次开菜单还会把通道认领回来，无限重复 |
| UI 桥降噪 | 首次桥解析遇到「UI 里没找到 BSMissionMenu 条目」也降为 INFO（菜单刚开的头几帧是预期状态） |

### 六·补四、第 26 轮：「引导未生效」的三次假失败 —— 确认窗口改绑菜单状态

**起因**（2026-09-20 10:38~10:58 三个会话的日志复查）：出现三次
`引导未生效：… 脚本状态一直是 0`（星海派对 / 回收行动 / 失踪的地球人）——明明有引导
目标、写入通道也成功，却全被判「脚本没响应」并清掉通道（界面回滚「引导未生效:脚本未响应」）。

**证据链（DLL 日志 × Papyrus 日志交叉）**：

* Papyrus 日志（`Papyrus.0~3.log`）里：`引导已应用` **只出现在菜单关闭那一刻**
  （`Papyrus 10:41:56 引导已应用` ↔ DLL `10:41:56.097 菜单关闭`，一一对应）；
  三个会话**都没有 `OnInit`**、也没有任何一条「菜单开着时」的引导应用。
* ⇒ 脚本实例从存档恢复时 `OnInit` 不跑 ⇒ `StartTimer` 从未注册 ⇒ **菜单开着时脚本不会轮询**，
  引导只在关闭事件里被应用一次。
* 唯一一次 `引导已生效`（绝非虚言）是因为玩家在 **1.6 秒内**就关了菜单。
* 旧逻辑：下发后 900ms 起确认，≈11 秒超时 ⇒ 玩家在菜单里挑条目超过 11 秒 = 假失败 + 真失效。

**修法（两侧）**：

| 侧 | 改动 |
| --- | --- |
| DLL `PollGuideVerify` | **菜单还开着时不判失败**：状态仍是 0 就继续等（不计数、不 Abort，每个请求打一行 `引导确认：脚本状态还是 0，但菜单还开着 …`）；状态 1/4 与重发（2/3，≤2 次）逻辑不变，重发改用独立计数 `verifyResends` |
| DLL `OnMissionMenuClosed` | 菜单关闭 = 脚本真正拿到请求的时刻：若还有未确认的下发，把确认窗口**重置**（900ms 首验 + 6×2s）并打 `引导确认：菜单已关 …`。超时判定只发生在菜单关着时 |
| 脚本 `SAQ_Main.psc` | 菜单打开事件里 `StartTimer` 重挂定时器（补齐实例恢复后缺失的轮询）+ `ApplyGuide()` 补一次（处理「菜单关着时 DLL 重发的请求」）；若引擎允许，引导在菜单开着时 0.5 秒内即应用 |

**实测判据（下次进游戏）**：

* 菜单里点一条有目标的条目后**不关菜单**：日志应出现
  `引导确认：脚本状态还是 0，但菜单还开着 …`，**不应**再出现 `引导未生效`；
* 关菜单：应出现 `引导确认：菜单已关 …`，随后 ≤11 秒内
  `引导已生效：… 脚本状态=1`（菜单关着也能记）；
* 若脚本重挂定时器生效：菜单开着时应直接看到 `引导已生效`（1~2 秒内），
  且 Papyrus 日志里 `[SAQ] 引导已应用` 的时间不再与「菜单关闭」绑定；
* 菜单里连点/切换多条：只有最后一条会生效（语义正确 —— 通道只有一个目标）。

测试期列表有 250+ 条，想验证某一件事（引导 / 界面回滚 / DLC）时，在列表里滚动找

> mod 的 GLOB**。所以 ini 是主通路；控制台那条留着碰运气（能认就用）。

| --- | --- |
| ESM（`patch_saq_esm.py`） | 保证存在 GLOB `SAQ_TestMode`（记录号 0x804，初值 0）。已存在则**保留当前值**（重新构建不会清掉你的设置） |

### ★ 第 31 轮：候选链改「**精确目标优先**」+ 引导目标动态更新

**起因（玩家反馈 + 13:15 截图）**：任务板的蓝点停在板子**旁边 2~3 m**。日志证据：

```
[13:11:54] 入口=12(可导航 12｜marker 0 原板 2 兜底 10 不可用 0)
[13:11:57] 引导请求：任务板 · 陋室（0x00137573）→ 引用 0x0011B754 …   ← 兜底引用，不是板
```

两层原因：

| # | 原因 | 证据 |
| --- | --- | --- |
| 1 | 11 条**新建常驻 marker 全部取不到**（`marker[未命中]`）—— 引擎里根本没有这些引用 | 第 30 轮设计的「任意位置精确导航」落空；新增 `入口 marker 探测` 日志专门定位它 |
| 2 | 于是目标落到「同 cell 最近的原生常驻引用」= **兜底**，它们离板 1.8~8.1 m（见下表）—— 蓝点当然不在板上 | 陋室那条就是 `MQ204_NoelBasement_Marker01a`（沙盒标记），距板 **3.41 m** = 截图里的偏差 |

★ 关键疏漏：第 30 轮的顺序是 `marker → 原板 → 兜底`，把**兜底排在原板前面**。而玩家走到板前时
板所在 cell 已加载 ⇒ **任务板引用自身其实取得到**（非常驻引用只要 cell 加载就存在），
它才是「精确 = 距离 0」的目标，却永远轮不到。

**改法一：顺序改成精确优先**（`EvaluateEntryGuide`，DLL）

```
① 任务板引用自身        精确（距离 0；cell 加载时可用，且引擎会给它高亮）
② 新建常驻 XMarker      精确（设计上任意位置可用 —— 目前实测取不到，见探测）
③ 同 cell 原生常驻引用   大致位置（1.8~8.1 m；只用于「板所在 cell 还没加载」时给个方向）
```

**改法二：目标**动态更新**（`UpdateEntryGuideTarget`，菜单关着时每 1.5 s 一次）**

玩家「站在别处选 → 飞/走过去」是常见走法，只改顺序还不够（选的时候只能拿到兜底）。所以：

| 时刻 | 目标 | 日志 |
| --- | --- | --- |
| 在霓虹城选「任务板 · 陋室」 | 兜底 0x0011B754（板还没加载） | `引导请求：…→ 引用 0x0011B754（同 cell 常驻兜底（大致位置））` |
| 走进陋室（cell 加载） | **换成板自身 0x00137573**，蓝点随之上板 | `入口引导目标已更新：…0x0011B754 → 0x00137573（任务板自身（精确））` |
| 离开陋室（cell 卸载、板引用消失） | 换回兜底（蓝点回到大致位置，HUD 仍指着） | 同上，末尾带「（原目标已不可用）」 |

细节与安全阀：

* 只在**菜单关着**时复算（菜单开着时脚本本来就不响应，换目标没意义）；
* 静默更新**不碰界面**（uID 没变，界面上的「正在引导」无需变化）；
* 静默更新的确认失败（脚本没响应）时**不清通道、不回滚界面**（`verifySilent`）——
  这是我们自己发起的优化，不该把玩家原本可用的引导一起清掉（区别见 `AbortUnverifiedGuide`）；
* 不会「精确 → 兜底」地乱跳：当前目标还活着时只在能换到更精确的才换。

**改法三：marker 取不到的探针**（`LogEntryMarkerProbe`，每会话一行，只在有兜底条目时打）

```
入口 marker 探测：XMarker 基类(0x00003B)=有｜通道前缀=0x0F（GLOB 认领值，兼作 marker 序号）
｜marker 0x90A@0x0F=无｜该记录号在别的序号上=无｜对照 QUST@0x0F=有
```

* 基类无 ⇒ 记录会被引擎丢掉（XMarker 0x3B 不存在）；
* 别的序号命中 ⇒ 「通道前缀 ≠ 插件序号」（GLOB 和引用被放在不同序号空间）；
* 对照 QUST 有 + marker 无 ⇒ **序号映射没问题，问题在 CELL 组里的新引用没被引擎加载**
  （下一步排查方向：Starfield 对「插件往 master 的 cell 里新增引用」的处理，见 `docs/99` 一·补十六）。

**12 条任务板的兜底距离（离线数据，`ref/entry_persistent_scan.json`）**：

| 任务板 | 兜底引用 | 距板 | 兜底引用是什么 |
