## 一·补二十一、第 36 轮：「设定航线（R）」对齐原版 —— 打开星图 / 展示目标星球

`dispatchEvent(MissionMenu_PlotToLocation{questID, objectiveID})` —— 引擎按 questID 查
**真实任务** → 取目标位置 → 打开星图 / 设航线。我们的可接任务在引擎侧不存在
（未接取，`IsRunning=false`），把它的 uID 丢进去只会静默失败（第 10 轮因此改成「自己引导」）。

**本轮修法：用代理任务当载体走回原版流程。** 代理任务（`SAQ_MainQuest`）是**真实存在**的

⇒ 满足引擎「取目标位置 / 画标记」的全部条件。所以按 R **新设定**引导的那一刻，额外把
代理任务交给原版流程：

| 层 | 改动 |
| --- | --- |
| DLL（`SAQ_UI.cpp`） | 载荷新增 `P\t<代理任务FormID>` 行（= `(通道前缀 << 24)｜0x800`；前缀是运行期才知道的，取不到写 0）；推送日志补 `代理任务=0x…` |
| AS3（`MissionMenu.as`） | 解析 `P` 行 → `SaqProxyQuestID`；按 R 新设定引导后调 `SaqPlotToLocationViaEngine()`：dispatch 原版 `MissionMenu_PlotToLocation{questID: 代理任务, objectiveID: -1}`（**取消**引导时不发）；`SAQ_Report` 多 `proxy=0x…`，guide 段追加 `｜星图:已请求(代理任务 0x…)` |

## 一·补二十二、第 37 轮：SET COURSE（R）的星图真正落地 —— 第 36 轮那条 dispatch 被证明**引擎无 sink**

**玩家反馈**：按 R 仍然只有「选中/取消选中条目」的效果，星图没打开。日志证明 AS3 侧
确实发了请求（`guide=…｜星图:已请求(代理任务 0xf000800)`、`proxy=0xf000800`）——
正是第 36 轮判据里写好的那个分支：**请求发了、引擎没响应**。

### 1. 定案（离线、可复现）：这类 `MissionMenu_*` 事件在 C++ 侧没有 sink

新增可复用逆向工具 **`tools/re/event_sink_probe.py`**（判据来历写在它的 docstring 里）：

```
python tools/re/event_sink_probe.py MissionMenu_PlotToLocation MissionMenu_ShowItemLocation
python tools/re/event_sink_probe.py DataMenu_PlotToLocation MissionMenu_ToggleTrackingQuest
  四个事件：事件源单例除「自己的静态初始化」之外**没有任何「读」**
  => 没有 C++ sink，dispatch 这个事件不会有任何效果
```

* `MissionMenu_PlotToLocation` 名字在 `.rdata 0x4C80AC0`，唯一引用它的代码是它的静态初始化
  函数 `0x15DF0F0`；事件源单例 `0x5F31A30` 的 5 处引用全在该函数内（另一处 `0x39A4CE0` 是
  引擎给所有事件源单例装共享 vtable `0x4B03D20` 的静态构造 —— 是**写**，不是 sink）。
* ⇒ **「照抄原版 AS3 那一行」在星图这件事上不可能成功**（不是 questID / 代理任务状态不对）。
  同族的「在地图上显示」（`MissionMenu_ShowItemLocation`）也一样。
* 顺带产出 `tools/re/dis_range.py`：带「RIP 目标注释」的反汇编（本轮手算偏移错一位，
  白追一轮，此后这类活一律用它）。

### 3. 根因：`kHide` 只隐藏**子**菜单，暂停菜单还开着 ⇒ 游戏仍暂停 ⇒ 定时器不走

* Starfield 的暂停菜单是**外层菜单**（带 tab 栏），任务菜单是它的子菜单。只 `kHide`
  BSMissionMenu ⇒ 停在暂停菜单顶层（= 玩家看到的「最外层主菜单」），游戏**没有恢复运行**；
* Papyrus 定时器只在游戏运行时走（第 27 轮定案）⇒ 脚本那 0.5 秒的星图定时器一直冻着，
  直到玩家自己把暂停菜单关掉（4~5 秒后）才触发 ⇒「要等好久」；
* 第 37 轮的探测是 **2.5 秒单点判定** ⇒ 每次都在星图出现之前就记下「没有打开」，
  日志给的结论是假的（星图其实开了）。
* ★ 顺带纠正一个名字：exe 菜单名表（`.rdata 0x4D7DF00` 一带，`tools/re` 可复现）里是
  **`PauseMenu`**（外层）+ `BSMissionMenu` / `MapMenu` / `SkillsMenu`…（tab）；
  **没有 `DataMenu`** —— 那只是 AS3 事件前缀（`DataMenu_SetMenuForQuickEntry` 等）。

## 一·补二十四、第 39 轮：R（SET COURSE）**不再取消引导**（已引导的条目再按 R = 再开星图）

（完整技术细节见 **`docs/05-任务引导.md` 第十三节**；本节记决策与验证。）

### 1. 玩家反馈（原文）

> 「在可接任务 tab 中，R 键具有选中/取消选中任务条目的效果，这在其他 tab 中是没有的，
> 这就导致了如果一个任务已经被选中跟踪，再点 R 键，就是取消选择条目，而不会打开星图，
> 这应该是个多余的功能。原版游戏的表现是：在未选中的情况下，按 R，进入星图显示任务位置，
> 然后弹窗询问你是否要跟踪，如果已选中，则直接在星图中显示目标位置。」

### 2. 根因：三个调用方共用了「切换取消」语义

`SaqToggleGuide(entry, wantMap)` 原本「同一条再按一次 = 取消引导」。这对
**Enter（点子项「前往接取地点」= 原版「点目标切换追踪」）** 正确，但
**R / 手柄 X（`OnPlotCourseEvent`，SET COURSE）** 借用它之后：
已引导的条目再按 R = 取消引导（竖条灭 = 玩家眼里的「取消选中」），而且取消方向永远
`wantMap = 0` ⇒ DLL 不去开星图 ⇒「星图完全没打开」。

### 3. 修法（只改 AS3 一处；DLL / Papyrus / 协议都不动）

| 改动 | 说明 |
| --- | --- |
| `SaqToggleGuide(entry, wantMap, allowUntoggle = true)` | 第三参数 = 是否允许「同一条再按一次 = 取消」。传 false 时：同一条上再按 = **保持引导**，本次请求退化为「把这条再交给星图显示一次」（seq +1 / quest 不变 / wantMap = 1 / pendingClose = 1） |
| `OnPlotCourseEvent`（R / 手柄 X） | 传 `false`（**永不取消**）；`SaqPlotToLocationViaEngine()` 每次都发（第 37 轮已证明引擎无 sink，这条只剩日志证据 + 音效） |
| 未引导时 | 行为与第 37/38 轮完全一致：设引导 + 关菜单 + 开星图 |
| 取消引导的正路 | Enter 选中子项「前往接取地点」（param3 默认 true，切换语义保留） |

**为什么 DLL 不用改**：`PollGuideRequest` 的去重判据是**序号变化**（不是任务是否变化），
所以「同一条任务 + 新序号 + wantMap=1」会被照常处理：再写一遍通道（状态 5）→
回写 `SAQ_GuideReply(seq, 同一条, 0)` → 界面命中「实际值 = 本地值 且 结果码 0」分支 ⇒
`CloseMenu(true)` → 脚本再开一次星图。日志里两种按法可分辨：
`已设为引导:<任务名>`（首次）vs **`重复设定航线:<任务名>`**（已引导时再按 R）。

### 4. 与原版的差别（如实记录）

原版「未追踪时先弹窗问是否追踪」这一步**不做**：星图是
`Game.ShowGalaxyStarMapMenuAndPlotToLocation(Location)` 打开的（传**地点**，不是任务），
引擎没有「要不要追踪这条任务」的上下文；而我们的引导（蓝点 + 路径线）本来就要求先把
代理任务设为追踪。玩家可见的收益（按 R 就能看到目标星球 + 航线）不受影响。

### 5. 验证（已做）

* AS3 重编译 + 部署：`build-saq.ps1 -SkipTable -SkipPapyrus -SkipPlugin` ⇒
  SWF 725886 / 726145 B + MO2 部署完成；
* `verify_saq_build.py` **全部通过**（新增特征：两个 SWF 里的 `重复设定航线:` note；
  旧特征与反向检查全在）。

### 6. 待实测判据（下次进游戏）

* ⇒ 「地点 → 行星」成立 ≠ 「地点 → 星图节点」成立（同一解析器的两种用途），
  所以「脚本日志里行星是对的」并不能证明星图会定位到那里。

## 十一、★★ 第 37 轮：SET COURSE（R）的星图真正落地 —— 第 36 轮那条 dispatch 被证明**引擎无 sink**

**玩家反馈**（第 36 轮部署后的实测）：按 R **仍然只有「选中/取消选中条目」的效果**，
星图没打开。日志证明 AS3 侧确实发了请求（`guide=…｜星图:已请求(代理任务 0xf000800)`
+ `proxy=0xf000800`），也就是**请求发了、引擎没响应** —— 第 36 轮判据里写好的那个分支。

### 11.1 定案：这类 `MissionMenu_*` 事件在 C++ 侧**没有 sink**（离线、可复现）

新工具 `tools/re/event_sink_probe.py <事件名>`（判据的完整来龙去脉写在它的 docstring 里）：

```
python tools/re/event_sink_probe.py MissionMenu_PlotToLocation MissionMenu_ShowItemLocation
python tools/re/event_sink_probe.py DataMenu_PlotToLocation MissionMenu_ToggleTrackingQuest
  四个事件全部：事件源单例除「自己的静态初始化」之外**没有任何「读」**
  => 没有 C++ sink，dispatch 这个事件不会有任何效果
```

细节（可复现的地址）：`MissionMenu_PlotToLocation` 的名字在 `.rdata 0x4C80AC0`，
唯一引用它的代码是它的静态初始化函数 `0x15DF0F0`（构造 BSFixedString → 注册进全局事件表），
事件源单例 `0x5F31A30` 的全部 5 处引用都在该函数内；另一处 `0x39A4CE0` 是引擎给
**所有**事件源单例装共享 vtable（`0x4B03D20`）的静态构造（是**写**，不是 sink）。

⇒ 结论：**「照抄原版 AS3 那一行」在星图这件事上不可能成功**（不是我们的 questID 不对、
不是代理任务状态问题，而是这个事件根本没人处理）。`MissionMenu_ShowItemLocation`（原版
「在地图上显示」）同族同命 —— 值得记住：**碰到 `XxxMenu_SomeEvent`，先跑一遍
`event_sink_probe.py` 再决定要不要照抄。**

### 11.2 引擎真正提供了什么

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| `Game.ShowGalaxyStarMapMenuAndPlotToLocation(Location aLocation)` | `Data\Scripts\Source\Base\Game.psc`；**原生实现 `0x2010210`** | ★ 本轮用的就是它：**打开星图 + 把航线画到该 Location**（原版 SET COURSE 的同款行为）。注册处 `0x2010740`（`Game` 脚本的原生函数注册大函数）里与 `ShowGalaxyStarMapMenu`（实现 `0x2010170`）相邻 |
| `Game.ShowGalaxyStarMapMenu()` | 同上 | 只打开星图（不带航线）—— 没用上 |
| 星图菜单的**注册名** | ★ 第 41 轮更正：引擎 `ShowGalaxyStarMapMenu*` 调用的 `0x253CFA0`（惰性初始化的静态 BSFixedString，`.rdata 0x4C96340`） | **`GalaxyStarMapMenu`**。（第 37 轮曾误用菜单名表 `.rdata 0x4D7E010` 里的 `MapMenu` —— 那是**另一个**菜单的名字，导致第 37~40 轮「星图没打开」全是假阴性，见第十五节。）DLL 用它做「星图有没有打开」的判据 |

### 11.3 本轮的实现（三层，各一层职责）

```
AS3（MissionMenu.as）
  R（OnPlotCourseEvent）→ SaqToggleGuide(entry, true)    ← 第二参数 = 要星图
  Enter（点「前往接取地点」子项）→ SaqToggleGuide(entry)  ← 默认 false，只要蓝点
  请求经 `SAQ_PeekGuide` 变成三段：`<序号>|<任务FormID>|<1/0>`（旧 SWF 两段 ⇒ 按 0）
  报告里多一段 ` map=1/0`（日志证据）

DLL（SAQ.cpp）
  ① 只有 wantMap=1 的请求写 `SAQ_GuideState = 5`（= 待处理 + 应用后打开星图）；
     普通请求仍写 0（重发 / 动态更新 / 静默更新 / 取消 一律 0）
  ② 写成功后用引擎的 UI 消息 `UIMessageQueue::AddMessage("BSMissionMenu", kHide)` 关掉任务菜单
  ③ 2.5 秒后探测结果并写日志：`星图：已打开（MapMenu 在屏幕上）` /
     `星图：没有打开（MapMenu 不在屏幕上）` / `星图：任务菜单没被关掉（kHide 无效）`

Papyrus（SAQ_Main.psc）
  菜单关闭事件 → ApplyGuide() 看到状态 5 ⇒ 照常应用引导（蓝点/路径线）+
  记下目标、`StartTimer(0.5, StarMapTimerID)`
  → OnTimer(StarMapTimerID) → OpenStarMapFor(target)：
       loc = target.GetCurrentLocation() ?? target.GetEditorLocation()
       Game.ShowGalaxyStarMapMenuAndPlotToLocation(loc)
```

**为什么必须由脚本 + 关菜单来完成**（而不是 DLL 直接开星图）：

* Papyrus 定时器在**任务菜单开着时不走**（第 27 轮三次会话实测定案）⇒ 脚本只能在
  「菜单关闭」事件里跑；玩家按 R 之后必须离开菜单，脚本才有机会开星图 ⇒ 由 DLL
  自己关菜单（`kHide`），交互上等价于原版：**按 R ⇒ 星图出现并画好航线**。
* DLL 直接调 `0x2010210` 要伪造 Papyrus 栈帧（参数是 VM 变量里的 Location 句柄），
  风险远大于收益；而脚本侧只要两行原生调用。

### 11.4 实测判据（下次进游戏）

## 十二、★★ 第 38 轮：修「R 键现象混乱」—— `kHide` 只关子菜单的坑 + 目的地诊断

**玩家反馈**：按 R「有时候只是切换到了最外层主菜单，有的时候打开了星图但要等好久，
R 键不会帮我选中这个任务，有时候星图显示的还是我所在的星球、也没有任务导航点，

### 12.1 定案（实测日志，15:52~15:55 会话）

三次按 R 完全同构：`kHide` 之后 DLL 看到「菜单已关」、脚本也应用了引导，
但脚本的 **0.5 秒定时器实际 4~5 秒后才跑**，而 2.5 秒的单点探测每次都提前判了

根因：Starfield 的**暂停菜单（注册名 `PauseMenu`）是任务菜单的父级**，只 `kHide`
任务菜单 ⇒ 停在暂停菜单顶层（= 玩家看到的「最外层主菜单」），**游戏没有恢复运行** ⇒

> `BSMissionMenu` / `MapMenu` / `SkillsMenu` / `StatusMenu`…（tab）；
> **没有 `DataMenu`** —— 那只是 AS3 事件前缀（`DataMenu_SetMenuForQuickEntry` 等）。

> ★ 第 41 轮再补一刀：这张表里**也没有 `GalaxyStarMapMenu`**（星图的真正注册名 —— 它由
> 引擎自己的 `ShowGalaxyStarMapMenu*` 经 `0x253CFA0` 引用）。「表里有」不等于「就是星图的
> 注册名」：当初从这张表里挑 `MapMenu` 就是这个坑（见第十五节）。

## 十三、★ 第 39 轮：R（SET COURSE）**不再取消引导** —— 已引导的条目再按 R = 再打开星图

**玩家反馈**（第 38 轮部署后的实测）：

> 「在可接任务 tab 中，R 键具有选中/取消选中任务条目的效果，这在其他 tab 中是没有的，
> 这就导致了如果一个任务已经被选中跟踪，再点 R 键，就是取消选择条目，而不会打开星图，
> 这应该是个多余的功能。原版游戏的表现是：在未选中的情况下，按 R，进入星图显示任务位置，
> 然后弹窗询问你是否要跟踪，如果已选中，则直接在星图中显示目标位置。」

### 13.1 根因（AS3 一处语义错位）

`SaqToggleGuide(entry, wantMap)` 的**三处调用方**原本共用「同一条再按一次 = 取消」的
切换语义：

| 调用方 | 语义 | 是否该切换取消 |
| --- | --- | --- |
| Enter（点「前往接取地点」子项，`onMissionListItemActivated`） | 对应原版「点目标切换追踪」 | ✅ 该 |
| 自动取消（`SaqAutoCancelIfAccepted`：玩家已接到这条任务） | 内部清理 | ✅ 该（走另一条路） |
| **R / 手柄 X（`OnPlotCourseEvent`，SET COURSE）** | 对应原版「显示目标位置」 | ❌ **不该** |

R 走切换 ⇒ 已引导的条目再按 R 变成「取消引导」：玩家看到竖条灭掉（= 取消选中）且
**星图完全没打开**（取消方向永远带 `wantMap = 0`，DLL 不会去开星图）。这与原版
「R = 显示目标位置（未追踪时再问一句是否追踪）」完全不符。

### 13.2 修法（只改 AS3，协议不变）

```
SaqToggleGuide(param1:entry, param2:wantMap, param3:allowUntoggle = true)
  · param3 = false 时：同一条上再按 = **保持引导**（不取消），本次请求退化为
    「把这条再交给星图显示一次」→ 序号 +1、wantMap = 1、pendingClose = 1
  · 唯一传 false 的地方 = OnPlotCourseEvent（R / 手柄 X）

R 的两种情形
  ① 未引导：seq++ / quest = uID / wantMap = 1 →（原有链路）引导 + 关菜单 + 开星图
  ② 已引导：seq++ / quest **不变** / wantMap = 1 → DLL 再写一遍通道（状态 5）
           → 回写成功 → 界面 `CloseMenu(true)` → 脚本再开一次星图
  取消引导仍有一条明路：Enter 选中子项「前往接取地点」（默认 param3 = true）
```

DLL 侧无需改动：`PollGuideRequest` 的去重判据是**序号变化**（不是任务是否变化），
`ApplyGuideRequest` 对同一条任务再写一遍 → `SetGuideTarget(..., a_starMap=true)`
（状态 5）→ `NotifyGuideReply(seq, 同一条, 0)` → 界面 `SAQ_GuideReply` 命中
「实际值 = 本地值 且 结果码 0」分支 ⇒ `SaqReturnToGameForStarMap()`。

日志可分辨两种按法（`SAQ_Report` 的 `guide=…` 段 / DLL 的 `引导请求：…｜星图=是`）：
`已设为引导:<任务名>`（首次）vs **`重复设定航线:<任务名>`**（已引导时再按 R）。

### 13.3 与原版的差别（如实记录）

* 原版「未追踪时先弹窗问你是否追踪」这一步我们**不做**：星图是用
  `Game.ShowGalaxyStarMapMenuAndPlotToLocation(Location)` 打开的（传的是**地点**，
  不是任务），引擎没有「要不要追踪这条任务」的上下文；而我们的引导（蓝点 + 路径线）
  本来就要求先把代理任务设为追踪。玩家侧的收益（按 R 就能看到目标星球 + 航线）不受影响。
* 从星图返回仍是回到游戏（不是叠在任务菜单上）—— 见 12.4 的备选路线。

### 13.4 验证（已做）与判据（待实测）

* 全量构建（`build-saq.ps1 -SkipTable -SkipPapyrus -SkipPlugin`）+ 部署；SWF
  725886 / 726145 B；`verify_saq_build.py` **全部通过**（新增特征：SWF 里的
  `重复设定航线:` note）。

  ③ 回归：Enter 点「前往接取地点」子项仍可切换/取消引导；无目标条目仍只有界面提示。

  （看 `重复设定航线:` 这条 note 在不在 DLL 的 `界面状态[…]` 行里）。

## 十四、★★ 第 40 轮：R 的星图「开不起来」+「指错星球」—— 引擎节点解析器 + 自动重试

**玩家反馈**：「R 键可以打开星图导航，但所有的任务都被导航至沃利阿尔法星，感觉还是有问题」。

### 14.1 日志复查给出的两条独立事实

| 事实 | 证据（16:28 会话，Papyrus.2 × DLL 日志） |
| --- | --- |
| 脚本那一半是好的 | 两次按 R 都执行到 `Game.ShowGalaxyStarMapMenuAndPlotToLocation(地点)`；地点/行星都对（`StationTheKeyInteriorLocation`→Suvorov、`CityNewAtlantisLocation`→Jemison） |
| ~~**但星图根本没开**~~ ★ 第 41 轮更正：假阴性 | 当时 DLL `CheckStarMapOpened` 每帧查 `MapMenu`，12 秒窗口**一次都没有** —— 但**查错了名字**（真名是 `GalaxyStarMapMenu`）：星图其实开了；中途那行「还开着：无」同理不可信（见第十五节） |

⇒ **修法 A**：脚本延时 0.5 → **1.5 秒**；DLL **自动重试**（见 14.3）。

### 14.2 ★ 引擎的「地点 → 星图节点」解析器（离线、可复现；本轮的关键发现）

`ShowGalaxyStarMapMenuAndPlotToLocation` 的原生实现 **`0x2010210`** 的完整骨架：

```
0xac2ab0(&节点, 地点)            ; 地点 → 星图节点（本轮的「判据函数」）
0x231f9b0(&dword0, 节点)         ; 由节点算出载荷第一个 dword
payload = { dword0, 节点 }       ; 8 字节
0x253cfa0(...) → 菜单名指针      ; ★ 第 41 轮更正：是 "GalaxyStarMapMenu"（不是 "MapMenu"）
0xC83790(queue, "GalaxyStarMapMenu", kShow, 描述符 @.data 0x5F59BA8, &payload)
```

* `0xac2ab0` 内部：读 `地点->formID`（`TESForm::formID` = +0x28，commonlibsf 已确认）→ 查
  「节点表」（`0x23ff640()` 单例 +0x8B0 → +0x238，哈希键 = `{formID, 全局 word, bit16}`）；
  没命中就调 `0xac2c20` 现场算，算出来再插回表里（= 缓存）。
* `0xac2c20`（节点匹配主体）：遍历节点表，键是 **64 位**：高 32 位 → `LookupByID` 必须是
  **LCTN(0x75)**，低 32 位是另一个 formID；取 `[LCTN+0xC0]`（父地点）的 formID 后，
  与**传入地点自身、以及沿 `[地点+0xC0]` 往上的每一层**的 formID 比对；命中则
  `*out = 节点->0x10 >> 16`（= 该地点的**行星** PNDT 的 formID）。
* **`0x1FEACE0` = `Location.GetCurrentPlanet()` 的实现**：`0xac2ab0` 出来的值必须能查到
  **PNDT(0xBA)** 记录，否则返回 null。
  ⇒ **同一个解析器、两种用途**：「地点 → 行星」成立**不代表**「地点 → 星图节点」成立。
  这就是为什么「脚本日志里行星是对的」仍然可能开了个指错地方的星图。
* 复现命令（都在 `tools/re`）：`python tools/re/dis_range.py 0x2010210 0x2010300` /
  `0xac2ab0 0xac2b90` / `0xac2c20 0xac2e80` / `python tools/re/func.py rip 0x5F59BA8`。

### 14.3 本轮的实现（三层）

| 层 | 改动 |
| --- | --- |
| 脚本 `SAQ_Main.psc` | ① `StarMapDelay = 1.5`；② 三个**地点候选**（由 `SAQ_GuideState` 的 5/6/7 指定）：**5 = 优先「行星自己的地点」** `Planet.GetLocation()`（新默认）／6 = 引用当前/编辑地点原样（旧行为）／7 = 父地点链里第一个带行星的地点；③ 日志：`父地点[i]=…（ID=…，行星=…）` + `…候选号=N，采用地点=…（ID=…）`；④ 两个小工具 `FormText/FormIDText`（避免 None 拼串） |
| DLL `SAQ.cpp` | ① **自动重试** `CheckStarMapOpened`：没开就每 2.5 秒重写「待处理 + 星图」状态（第 2/3 次改成 6/7 = 换候选），最多 3 次；只在「没有任何菜单开着」时重试（菜单开着 ⇒ 游戏暂停 ⇒ 脚本跑不到）；引导目标变了/取消 ⇒ 放弃；每次重试把窗口顺延 12 秒；成功那行日志写明**第几次尝试**。② **只读诊断** `LogStarMapDiagnosis`（按 R 时一次）：`引用 → 当前/编辑地点 → 逐层父地点`，每层调 `0xac2ab0` 打印 `节点=`/`标记=`，并打一行 `玩家所在地点=` 做对照（星图「站在原地」时就是它） |
| 引擎函数调用惯例 | RVA + **函数头 8 字节特征校验**（`4C 89 1C 24 49 89 5B 20`）+ `__try/__except` 全在**纯 POD 函数**里；拿不到函数指针就只写一行「节点解析器不可用」，绝不乱调 |

### 14.4 判据（下次进游戏）

### 1. 玩家反馈（原文）

### 2. 排查：两份日志对齐（18:34~18:35 会话，第 43 轮版本）

```

```

| 观察 | 结论 |
| --- | --- |
| 星图在 DLL 写完通道后 **9 毫秒**就被探测到（探测名已是第 41 轮修正过的 `GalaxyStarMapMenu`） | 打开它的**不是**脚本（脚本要等菜单关闭 + 1.5 秒延时）⇒ 只可能是 AS3 在按键那一刻**同步** dispatch 的那条原版事件 |

其实是生效的**（第 37 轮「引擎无 sink」的离线结论不成立：这条 dispatch 经 `BSUIDataManager`
的 AS3 事件通道被处理，静态扫描「事件源单例的引用」看不到它）。它的两个致命点：

1. 引擎取的是**该任务当前的目标位置** —— 我们传的是**代理任务**（`SAQ_MainQuest`），

   引用 ⇒ **位置永远滞后一条**；
2. 它把星图**先**打开了 ⇒ 游戏暂停 ⇒ 我们那条「用正确目标再开一次」的补救再也跑不到。

同一条机制还解释了此前三条反馈：「所有任务都被导航至沃利阿尔法星」（别名还空着 ⇒
引擎按默认焦点 = 玩家所在星球打开）、「有一次打开了其他任务的位置」（别名 = 上一条引导的目标）。

**B. ESM：11 条 CELL 记录（官方的「空壳」写法）**（`tools/esm/create_board_markers.py`）

先说**为什么不整条照抄 Starfield.esm**（这是本轮改过一版才定下来的）：

* 整条照抄 = 把 cell 的全部字段变成「本插件版本」⇒ 别的 mod 改过同一 cell 时会被覆盖；
* 基础游戏的 cell 名（`FULL`）是**本地化 string ID**（4 字节），而本插件非本地化 ——
  引擎会把它当内联字符串（xEdit 重存后显示成乱码），等于把 cell 名写坏。

改用的、也是**官方对同一条 cell 的写法**（`tools/esm/dump_cell_group.py --plugin SFBGS003.esm`
实测，对象正是任务板所在的霓虹城 `0x00071D5A`）：

```
GRUP Interior Cell Sub-Block 6
  CELL 0x00071D5A flags=0x004000 size=19 子记录=[EDID]     ← 空壳：只留 EDID，不写数据字段
  GRUP Cell Children of CityNeonCore [CELL:00071D5A]
    GRUP Cell Persistent Children …
      REFR 0xFD000F13 flags=0x000400                       ← 官方自己新增的常驻引用
```

⇒ 本插件现在写：**空壳 CELL 记录（EDID + flags 0x4000，非压缩）**，放在子块组的**第 0 个子项**，
紧跟它自己的 `CellChildren > CellPersistent > 我们的 marker`。**不碰 cell 的任何数据**，
也不覆盖本地化名称字段（连 cell 级冲突面都没有）。

| 层 | 改动 |
| --- | --- |
| 生成 | `create_board_markers.py`：`build_cell_stub()` + `record_edid_of()`（解压取 EDID）；重建时校验「Starfield.esm 的 cell EDID == entry_targets.json 的 cell」；自校验新增空壳断言（override 空间 / 组链尾部 [2,3] / flags 0x4000 / 非压缩 / 子记录恰好 `[EDID]` / EDID 相符） |
| 产物 | ESM 从 2948 B → **3521 B**（11 marker + 11 空壳；对比「整条照抄」那版是 1434623 B） |
| 验证工具 | `verify_saq_build.py`：ESM 数据侧解析新增「CELL 空壳 11/11」检查（工作区 + MO2 两份），并断言**不许**写数据字段 |
| xEdit 脚本 | `verify_persist.pas` 增加 CELL 记录计数（脚本必须保持纯 ASCII —— 踩过一次：中文注释直接让 xEdit 编译失败） |
