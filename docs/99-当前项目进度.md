## 三、第 10 轮：任务引导（本轮核心，实现见 `docs/05`）

需求里的「能调用游戏的任务引导系统正常引导到接取任务的地点」这轮落地了整条链路：

```
AS3 选中条目按 Enter/X → SAQ_PeekGuide() "<序号>|<任务FormID>"
  → DLL 轮询（100ms）→ 静态表取「引导目标引用」→ 写 GLOB（SAQ_GuideTargetRef + GuideState=0）
  → SAQ_Main.psc 0.5s 轮询/菜单关闭 → GetAlias(0).ForceRefTo(目标) + SetObjectiveDisplayed(10)
                                    + SetActive(true)
  → 引擎画任务标记（蓝点）+ 扫描仪路径线
```

三个关键决策（每一个都留了证据）：

| 决策 | 为什么 |
| --- | --- |
| 引导目标 = **任务发布者的放置引用 / 任务自己的落脚引用**（离线算，83% 覆盖） | 引擎只认「世界里的一个引用」；发布者就是「去哪里接」的答案。地点地图标记（`LCTN.MNAM`）只有 7% 的任务有，做兜底 |
| **优先常驻（persistent）引用** | 非常驻引用要等格子加载，玩家在远方时 `Game.GetForm` 拿不到 ⇒ 引导失败。168 条里常驻 100 条 |
| 通道用 **GLOB**，并靠脚本写的**魔数 7777** 反查自己插件的加载序号 | SFSE 没有「C++ 直接给 Papyrus 发事件」的接口；FormID 的高 8 位运行期才知道，不能写死 |

顺带把**身份锚点**变成了证据链：日志里 `通知=7777` ⇒ ESM 已加载、代理任务在跑、脚本活着；
值在涨 ⇒ 脚本看得到菜单开关事件。

### 3.2 本轮踩的坑（都已修）

| 坑 | 现象 | 结论 |
| --- | --- | --- |
| `write_esm` 用「原组大小 + 增量」 | 第一次写坏之后错误被继承，记录越过 GRUP 边界 | 改成**整体重新序列化 + 重算组大小**；读取用不依赖组大小的线性遍历 |
| 用黑名单重建记录 | 上一次运行残留的 `FNAM` 被带进来（记录里出现两个多余 FNAM） | 改成**白名单**（只保留 EDID/VMAD/DNAM/NAM3/NEXT…） |
| `AutoConst` 不存在 | Papyrus 报 `Unknown user flag autoconst` | Starfield 的 Papyrus 4.7 用 `AutoReadOnly` |
| 子记录解析没处理 `XXXX` | 长数据记录后面冒出一堆「四个零字节的签名」（实测 8 万个） | `subrecords()` 必须处理 XXXX 的 4 字节扩展长度 |
| 编辑器里「xEdit 说 3532 条 QUST」 | 与自写解析的 2077 条不一致 | xEdit 的 `quests_all.txt` 统计口径不同；**Starfield.esm 的 QUST 组真实记录数就是 2077**（组里还有 12 万条 INFO / 6.8 万条 DIAL） |
