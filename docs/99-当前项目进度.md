### 2.2 真凶：哈希的输入是「字符数据指针」，不是「string-pool Entry 指针」

重新逐条反汇编查表函数（RVA `0x2546170`，全文见 `docs/02` 第一节）：

```
mov  rsi, [rdx]              ; rsi = BSFixedString 里那唯一的 qword（Entry*）
mov  eax, [rsi+0x14] / 测试 kExternal 位
  → 不外挂：lea rcx, [rsi+0x18]     ; ★ 字符数据 = Entry + 0x18
  → 外挂  ：沿 [rsi+8] 走 leaf()（函数 0x28CAE80）
shr  rax, 0x20 / xor ecx, eax       ; ★★ 哈希 = charsPtr ^ (charsPtr >> 32)
and  rdx, [rbx-1]                   ; index
cmp  qword [rax+rcx], rsi           ; ★ 比较用的是 Entry*（不是 chars）
```

上一轮把**两个不同的指针**混成了一个：用 `Entry*` 去算哈希 ⇒ 每次都在**错的桶**里找，
链一走到空槽（`next == -1`）就报「没找到」。
（`commonlibsf::UIMenuNameHash` 内部用的是 `c_str()`，也就是字符指针 —— 它是对的；
错的是我们照着自己写的注释抄。）

### 2.4 顺带复核（离线，`tools/re/rtti_slots.py`）

- 全 exe 里含 `AVMovieRoot` 的类**只有 1 个**：`.?AVMovieRoot@AS3@GFx@Scaleform@@`
  ⇒ 「RTTI 名字含 MovieRoot」是**精确**判据（所以 Movie / ASMovieRoot 的扫描范围放宽也没风险）；
- 它的主 vtable = RVA `0x3BE32B0`，槽表 `[2C]=CreateString [2D]=CreateStringW [39]=0x3368DC0 Invoke`；
- ⇒ commonlibsf 的 Scaleform 侧声明可信，游戏类成员偏移（UI.formArrays / menuMap）不可信 —— 分开对待。

用户反馈：*「看上去是乱码，里面也没内容」*（截图：第 8 个 tab 显示 `$SAQ_Avail…`，列表空）。

### 2.1 取证：一行日志定案

```
[21:00:27.120] 首次菜单打开：quest 总数=0 可接候选=0 推送=失败 (第1次)
```

- `推送=失败`：`PushToUI()` 里 `UI::GetMenuMovie("BSMissionMenu")` 返回 null（**没走到 Invoke**）；
- `quest 总数=0`：`TESDataHandler::formArrays[kQUST]` 读到空表；
- tab 标题是 `$SAQ_AvailableQuests` 原文：C++ 那份"按语言选好的标题"根本没送到，
  而 `$` 开头的 token 走的是游戏的 `translate_*.txt`，里面当然没有我们的 key。

### 2.5 第 3 轮留下的、仍然有效的结论

- ★ **真实菜单表在 `UI+0x450`**（commonlibsf 标的 `menuMap@0x470` 在 1.16.244.0 上是错的）；
  表头：数据指针 `+0x38`、容量 `+0x40`；条目跨度 `0x38`：key `+0x00`、值 `+0x08`（0x28 字节）、
  nextIndex `+0x30`（`-1` = 空槽）；值 `+0x20` 就是 `Ptr<IMenu>`；
- 不再用 `TESDataHandler::formArrays`（本机实测全 0），改成按静态表 FormID 逐个
  `TESForm::LookupByID` 问引擎；
- 推送协议：一整段文本（`SAQ1 / T\t标题 / Q\tFormID\ttype\t名字`），AS3 侧自己解析
  —— 只依赖 `Invoke` 一个虚函数槽（数组式推送要 4 个槽，风险大得多）；
- 设计原则：**不缓存 commonlibsf 的游戏类偏移**，一律「实测偏移 + 扫描 + 自校验」，
  每一步都能失败但不能崩；每种尝试的结果都写日志，一轮实测就能定位。
