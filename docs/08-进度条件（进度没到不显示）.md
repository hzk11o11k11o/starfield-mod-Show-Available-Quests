# 08 · 进度条件（「游戏进度还不能让玩家接到 ⇒ 不显示」）

> 2026-09-20 第 35 轮。需求原文（AGENTS.md）：
> 「任务必须是可接的，如果当前游戏进度还不能让玩家接到对应任务，则不显示」。
>
> 这是需求里最后一个没有实质机制支撑的点（`docs/04` 第五节：🟡 只被「已开始」层
> 间接覆盖一部分）。本文记录：怎么把「进度门槛」这条判据从游戏数据里挖出来、
> 为什么只敢用其中一部分、怎么求值、怎么自证。

---

## 一、问题的形状

「进度没到」在游戏里有三种表达，成本完全不同：

| 表达 | 例子 | 能不能判定 |
| --- | --- | --- |
| 引擎自动启动类（faction/活动） | 引擎按条件自己 Start | ✅ 已被现有的「已开始」层间接覆盖 |
| **任务记录级条件（QUST 的 CTDA）** | 「大器晚成」要「孤立无援」完成 | ✅ **本文**（覆盖 261 条里的 7 条） |
| 对话选项条件（INFO 的 CTDA） | 「做完 A 后 NPC 才多一句对话」 | ❌ 工程量大（几十万条 INFO 的关联与求值），本阶段不做 |

真正的玩家感知大部分来自第二、三种；第二种有**直接可用的数据**：

```
FFConstantZ06「亲爱的姐妹」的记录级条件（xEdit 原文）：
  GetQuestCompleted(UC04 "Eyewitness") == 1      ← 前置完成
  GetQuestCompleted(FFConstantZ06 自己) == 0     ← 自己还没做过
  GetQuestCompleted(FFConstantZ04) == 1   [op=0x01]
  GetQuestCompleted(FFConstantZ05) == 1   [op=0x01]
```

## 二、CTDA 字节结构（实测定的，不是抄 commonlibsf）

`ref/quests.json`（原始 hex）与 `ref/xedit/quests_typed.txt`（xEdit 解码）配对验证
（`tools/esm/analyze_ctda.py`，p1 与 xEdit 的 Parameter #1 全部一致）：

```
偏移  类型   含义
0     u8     operator（0x00 = 等于；0x01/0xA0/0xA4 语义见下）
4     f32    比较值
8     u16    函数索引（GetQuestRunning=0x38 / GetStageDone=0x3B /
              GetInFaction=0x47 / GetIsID=0x48 / GetGlobalValue=0x4A /
              GetQuestCompleted=0x21F / LocationHasKeyword=0x232 …）
10    u16    （xEdit 显示为 Unused，常见 f9 44）
12    u32    参数 1（GetXxx 的任务引用；GetStageDone 里 = 目标任务）
16    u32    参数 2（GetStageDone 里 = stage 索引）
20    u32    Run On（0 = Subject；事件类是别的值）
24    u32    reference
28    i32    参数 3（常见 -1）
```

**未解的部分（本阶段刻意不碰）**：

* operator `0xA0/0xA4`（只出现在「位置/扫描/遭遇」类条件里）与 `0x01` 的精确语义
  没有反汇编定论 ⇒ **带这些位的条件一律不放行**（见第四节）。
* `0x01` 出现在 FFConstantZ06 的「Z04/Z05 完成」两条上，语义「像」OR，但没证据
  不猜 —— 代价只是这条任务的 gate 退化成「UC04 完成」（少过滤一点，不会误伤）。

## 三、★ 「门槛」的定义（保守到极致）

一条 CTDA 能当**进度门槛**，必须同时满足
（`tools/esm/analyze_ctda.py::build_gate`）：

1. `operator == 0x00`（等于比较，语义唯一确定）；
2. `Run On == Subject`；
3. 函数 ∈ { GetQuestRunning, GetQuestCompleted, GetStageDone }（DLL 侧可安全求值）；
4. 比较值 ∈ { 0.0, 1.0 }；
5. **引用的是「别的任务」**（`p1 != 自己`）。

第 5 条是踩过坑之后补的 —— **自引用条件不是进度门槛**：

> 第 11 轮实证：RAD05「全数到期」的记录级条件是 `GetQuestRunning(自己) == 0`，
> 引擎提前把它置成 running（flags=0x8001）—— 按「条件为假就隐藏」跑，会把一条
> **玩家明明还能接**的任务藏掉。这类自引用条件是引擎**启动流程的防重入守卫**，
> 描述的是「任务有没有在跑」，与「玩家能不能接到」无关。

任务的**全部门槛为真 ⇒ 显示；任一为假 ⇒ 隐藏（进度没到）；没有门槛 ⇒ 不做条件
过滤**。

当前覆盖（261 条里 **7 条任务 / 9 条条件**，全在基础游戏）：

| 任务 | 门槛 |
| --- | --- |
| FFNewAtlantis03 | UC04 未运行 |
| FFDenZ01 | UC01 到 stage 1000 |
| FFConstantZ06 | UC04 完成 |
| FFNewAtlantis01 | FFNewAtlantis03 到 stage 100 + UC04 未运行 |
| FFNewAtlantis02 | FFNewAtlantis03 到 stage 20 + UC04 未运行 |
| City_NA_Botany03（大器晚成 / Late Bloomer） | City_NA_Botany02（孤立无援 / Out On a Limb）完成 |
| FFNeonZ10 | City_Neon_Gang03 完成 |

> 其余 32 条带记录级条件的任务都含「位置/扫描/遭遇」类函数（依赖 event data /
> 当前星球），本阶段**不猜** ⇒ 放行。`docs/07` 的归因结论同样适用：宁可少过滤。

## 四、引擎侧求值（反汇编，非猜）

### 4.1 `GetStageDone` 拿到引擎实现

Papyrus `Quest.IsStageDone` 的实现（`ref/quest_natives2.txt`：`impl=0x20CB530`）
内部 `call 0xD0DBD0` —— 那才是真正的「stage 是否完成」：

```asm
00D0DBD0  mov r8d, [rcx+0x1AC]   ; stage 哈希表掩码
00D0DBD5  mov rbx, [rcx+0x1A0]   ; stage 哈希表（每项 4 字节：低 16 位 + 高 16 位下标）
00D0DBDC  movzx eax, dx          ; stage 参数
00D0DBE3  and r8, rax
00D0DBE9  mov r9d, [rbx + r8*4]  ; 0xFFFF???? = 空槽
00D0DBFC  mov r10, [rcx+0x140]   ; ★ stage 指针数组
00D0DC11  cmp word [rax+0x10], dx ; stage 对象 +0x10 = stage 索引
00D0DC58  test byte [rax+0x12], 1 ; ★ +0x12 bit0 = done 位
```

⇒ 新增知识：**TESQuest +0x140 = stage 指针数组、+0x1A0/0x1AC = stage 哈希表、
stage 对象 +0x10 = 索引、+0x12 = flags（bit0 = done）**。

### 4.2 DLL 怎么用它

* 直接调用 `bool __fastcall(TESQuest*, u16)@0xD0DBD0`（不再自己遍历哈希表 ——
  引擎的语义、引擎的实现，100% 一致）；
* 调用前做 **9 字节函数头特征校验**（`48 89 5C 24 08 44 8B 81 AC`）——
  换游戏版本后特征不符 ⇒ 完全不用它（返回 kUnknown ⇒ 放行），绝不错调；
* `__try` 只出现在**纯 POD 函数**里（MSVC 不允许 `__try` 与需要析构展开的对象
  共存 —— 项目已踩过，见 `SAQ_QuestState.cpp` 注释）。

`GetQuestRunning` / `GetQuestCompleted` 走已有的 `ReadQuestRuntimeState`
（flags 位 + 虚表核验，第 9 轮实测）。

## 五、判断语义（三态，保守优先）

`SAQ_QuestCond.cpp::EvaluateProgressGates` 返回四态：

| 结果 | 条件 | 行为 |
| --- | --- | --- |
| `kNoGates` | condCount == 0 | 正常显示 |
| `kPass` | 全部门槛为真 | 显示 |
| `kFail` | 有门槛为假 | **隐藏**（进度没到） |
| `kUnknown` | 目标取不到 / 状态读不了 / IsStageDone 不可用 | **放行**（按「没有门槛」处理） |

`kUnknown` 放行是刻意的：**误藏一条真任务比多显示一条难受得多**
（玩家报「某条明明能接却不显示」无法自解）。日志里 `未知` 计数会暴露这一类。

## 八、已知风险

* **语义假设**：「记录级条件为假 ⇒ 不会给接」对**外部引用**条件的成立概率很高
  （这些条目就是前置检查），但仍不是 100% 引擎级证明 —— 所以有 ini 开关、
  有名单日志，出问题一开关就能回到旧行为。
* **覆盖有限**：7/261 条（★ 第 48 轮起由「九、INFO 门槛」补上 60 条，见下）。
* **operator 未全解**：0x01/0xA0/0xA4 的语义没反汇编定论（0xA0/0xA4 只在
  遭遇类条件里出现）；一旦将来做遭遇类任务，需要先补这一课。
* `IsStageDone` 的硬编码 RVA（0xD0DBD0）绑定 1.16.244；换版本靠特征校验兜底
  （不符即放行，不会错调）。

## 九、★★ 第 48 轮（大项 D）：对话侧条件 —— INFO 门槛

> 需求原文（AGENTS.md）：「任务必须是可接的，如果当前游戏进度还不能让玩家接到对应任务，
> 则不显示」。第三节的记录级门槛只有 7 条；**玩家感知的大头在对话（INFO）侧**。

### 9.1 数据形状（离线全表扫描，`tools/esm/scan_info_gates.py`）

Starfield 与 Skyrim/FO4 不同：**对话挂在 QUST 的 children 组下**
（`GRUP type=10, label=quest FormID` → `DIAL` → `GRUP type=7` → `INFO`）——
**「INFO → 所属任务」从组链直接可得**（不需要过 DIAL 的 QNAM）。

Starfield.esm 实测规模：

| 项 | 数量 |
| --- | --- |
| QUST 记录 | 2077 |
| INFO 记录 | 126347 |
| 带 CTDA（条件）的 INFO | 8541 |
| 带 VMAD 的 INFO | 604 |
| 条件里「引用**别的任务**」的进度检查 | 613 条（涉及 307 个任务） |

### 9.2 ★ 判据设计（保守到极致，两例实测对照）

「任务自己的对话条件」不等于「接取门槛」，所以**先分类再合成**：

| 分类（按条件组里对该任务**自己**的引用） | 含义 | 参与判定 |
| --- | --- | --- |
| **入口类**：含「自引用 == 0」（如 `GetQuestRunning(自己)==0`） | 任务**还没开始**时才出现的对话 | ✅ |
| **中性类**：无自引用 | 无法区分入口/中途 | ✅ |
| **推进类**：含「自引用 == 1」（如 `GetStageDone(自己, x)==1`） | 任务**进行中**的对话（回报/分支） | ❌（绝不能拿来判接取） |

合成规则（`analyze_info_gates.py` → 静态表；运行时 `EvaluateInfoGates`）：

* **一条对话 = 一组条件（AND）**；只要「有一条**已知为假**」的条件 ⇒ 这条对话不可用；
* **全部参与判定的对话都不可用** ⇒ 隐藏（进度没到）；
* 任何一条对话「没有已知为假的条件」（条件全真 / 有不可判定项 / 求值不了）⇒ 显示；
* 任务里**任何一条参与判定的对话没有可判定条件** ⇒ 整条任务不进表（保守）；
* 只收 `want ∈ {0,1}` 的 `GetQuestRunning / GetQuestCompleted / GetStageDone`
  （形态与第三节记录级门槛完全一致）。

**为什么这套规则安全**：条件「成对」的任务（如 `X==0` 与 `X==1` 各有一条对话）
会自动豁免 —— 任何时刻至少有一条为真 ⇒ 永不隐藏。它只在「**全部**对话都被事件条件
挡住」时才隐藏，而这正意味着「玩家还没推进到这段剧情」。

**两例实测对照**（记录级门槛 ↔ INFO 条件完全一致）：

| 任务 | 记录级门槛（第 35 轮） | INFO 条件（本轮） | 一致 |
| --- | --- | --- | --- |
| 大器晚成（City_NA_Botany03） | 孤立无援（City_NA_Botany02）完成 | `GetQuestCompleted(City_NA_Botany02)==1` | ✅ |
| 亲爱的姐妹（FFConstantZ06） | UC04 完成 +（未解 op 的）Z04/Z05 完成 | `GetQuestCompleted(FFConstantZ05)==1` ×3 + `GetStageDone(FFConstantZ05,270)==1` | ✅ |

覆盖：**60 条任务 / 290 条对话 / 341 条条件**（全在基础游戏；DLC 的 INFO 待后续扩展）。
名单（按任务）：CF02/CF03/CF04/CF05/CF06/CF08_*、COM_Quest_*、UC01~UC09 系列、
FF 系列（大器晚成/孤立无援/亲爱的姐妹/外交豁免权/维护和平/特快专递……）、RI/RIR/FC/RAD、
City_* 杂项等。

### 9.4 已知风险

* **误藏**：若某任务的「全部事件条件对话」都被挡住、而它的接取另有途径（脚本/场景触发），
  会被误藏。缓解：成对条件自动豁免 + 交叉验证 WARN + ini 开关 + 名单日志（出问题可一条命令回到旧行为）。
* **DLC 未覆盖**：DLC 的 INFO 还没扫（保守：DLC 任务不做 INFO 判定）。
* **「无条件对话」被忽略**：任务自己的无条件对话大多是「运行中」的（引擎隐式要求
  quest running），拿它们当「入口」会让判据完全失效；忽略它们是**判据能工作的前提**，
  其风险由「成对豁免 + 交叉验证」兜住。
