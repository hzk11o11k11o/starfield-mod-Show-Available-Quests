> （crew faction 三件套）——**待实机验证**（不是阻塞项）。

## 16.1 枚举：谁是「可招募的有名字船员」

* **EDID 前缀判据**（推荐）：NPC_ 里 `Crew_Elite_*`，排除 `OtherPlayer*` 模板与
  `BalanceData*` 模板 ⇒ **实测 24 位**（见下表）。
* **官方 FLST 印证**：`CREW_imGui_2a_Actors_Elite`（0x00133A67，24 名成员）——
  与 EDID 判据基本重合，两处差集：
  * FLST 里有 `COM_CoraCoe`（Cora 是 Sam 的女儿，**无 crew faction、不可招募**）
    与 `OtherPlayerMale` 模板 ⇒ 判据要排除；
  * FLST 里**没有** `MathisCastillo`、`AdoringFan`（两人都有完整招募任务）
    ⇒ **FLST 会漏人，EDID 判据更准**。
* **每位对应 1 条招募载体任务**（QUST）：`CREW_EliteCrew_<姓名>`
  —— 实测 **25 条** = 24 位船员 + `CREW_EliteCrew_OtherPlayer`（玩家自身模板）。
  对话 / 分支 / 场景分别挂 `INFO` / `DLBR` / `SCEN`（同一前缀 + 后缀区分），
  另有 2 条 CNDF 条件（`CREW_CND_DIAL_RecruitRepeat` / `..._Greeting_Recruit`）。
* **NPC_ 上挂 VMAD 脚本** `EliteCrew_StartQuestOnLoadScript`（属性引用 `ECQuest`
  系）—— 每个船员加载时启动其招募任务，这是官方招募机制的入口。
* **crew faction 三件套**（23/24 挂载，initial rank 多数 255）：
  * `AvailableCrewFaction`（0x00014314）
  * `CurrentCrewFaction`（0x00014312）
  * `PotentialCrewFaction`（0x000143A2）
  * **例外 = Lin**（0x005638）：三个都没挂（主线剧情加入，faction 由脚本后期
    添加）⇒ 未来做「已招募/可招募」判定必须容错。
* 命名拼写坑：`ErickVonPrice`（NPC）↔ `CREW_EliteCrew_ErickvonPrice`（任务，
  小写 v）——按名字串匹配任务时要大小写不敏感。

**核心事实**：

1. **每人只有 1 处放置**（不是多地点同名实例）——与任务板 / 可重复 NPC 同构。
2. **23/24 是非常驻引用**（仅 Vasco 常驻）⇒ cell/world 未加载时取不到，
   与第 27/30 轮任务板当年的问题**完全同型**。
3. **XESP = 0**（24 处全都没有 enable parent）⇒ 位置是静态的，不随开关变化。
4. **兜底候选 100% 可用**：内景 11/11 cell 有同 cell 常驻引用（21~213 个 ≤25 m）；
   外景 5/5 world 有 world 级常驻引用（13~364 个 ≤25 m）
   ⇒ **不新建 marker 也能配出「精确引用 → 常驻兜底」候选链**（第 30/47/114 轮机制）。
5. **三处位置不适合直接导航**（建议「（不可导航）」前缀 + 点击提示，照第 91 轮）：
   * `MoaraOtero` → `MQHoldingCell`：**别名暂存格**（玩家永远到不了；`BAD_CELL_RE`
     判据本该命中）；
   * `BettyHowser` → `SEAC01...CreatedInterior`：太空遭遇**运行时生成**的船内景；
   * `ErickVonPrice` → `CargoShipJane01CreatedInterior`：货船**生成内景**。
6. 可导航但需到达条件（剧情锁 / 特殊地点，不阻塞）：
   星钥站（Jessamine / Mathis）、Vectera 矿场（Lin / Heller）、红英里（Autumn）、
   熔炉（Amelia）、Tau Gourmet（Hadrian）。**是否需要进度门槛**留待实现阶段另议。

## 16.3 「什么时候显示」的判据（待实机验证）

* faction 三件套**初始就挂着**（rank 255/1）⇒ 不能只凭「挂着」判「可招募」。
* 待实机探针（harness 只读）建议记录：
  1. 招募**前 / 后**，NPC 引用在三个 faction 的成员状态变化
     （`IsInFaction(AvailableCrewFaction / CurrentCrewFaction / PotentialCrewFaction)`）；
  2. 招募前 / 后，`CREW_EliteCrew_*` 任务的状态（`GetRunning / GetStageDone`）；
  3. Lin 的对照组（无三件套）——验证「剧情加入」路径。
* 隐藏策略候选：**已招募 ⇒ 隐藏**（用 `CurrentCrewFaction` 或任务状态判定，
  哪个可靠用实测数据说话）；未招募 ⇒ 显示（全部 24 位，其中 3 位带「（不可导航）」）。

### 2. 只读 harness 探针 `crew.probe`（驱动器 **v71**）

* 一次跑全表 24 位，每位两条路**配对**读出：
  1. **faction 侧**（Papyrus 新 op=7，`SAQ_Main.psc`）：`Actor.IsInFaction` 三件套 +
     `GetCrewAssignment` ⇒ 结果码 `16 + 状态位`（bit0 A / bit1 C / bit2 P / bit3 已分配）。
     **引用未加载的位直接跳过**（DLL 侧 `LookupByID` 预检 —— 与 Papyrus `Game.GetForm`
     同源），既省往返也如实记录（faction 是 actor 实例状态，远处读不到是引擎限制）；
  2. **任务侧**（DLL 直读 `ReadQuestRuntimeState`，与产品同一套判据）：招募任务
     `CREW_EliteCrew_*` 的运行状态**不依赖引用加载** ⇒ 24/24 总有结果 = 判据主证据。
* 红线六：逐位产品行 `船员探针 [i/24] 名字（0x…）｜Papyrus: …｜招募任务 …` +
  一行 `船员探针 汇总：…`（faction 读到位数 / A·C·P·分配 计数 / 任务状态分布）。
* 用例 **`r155_crew_probe`**（只读：不 reset / 不推 stage / 不传送）：
  断言 = 汇总行（产品行前缀，第 147 轮的教训）+ 三条**链路健康反向断言**
  （不许「失败（结果码…）」/「等回执超时」/「｜招募任务 表单取不到」）。

### 3. 判据线索（一手证据，待实机确认）

* 官方脚本 `Crew_RecruitQuestScript.Recruited()`（Data\Scripts\Source\Base）：
  `if CrewMemberRef.IsInFaction(SQ_Crew.AvailableCrewFaction) == false` ⇒ **只收首次招募费**
  ⇒ 「在 `AvailableCrewFaction` 里 = 曾经招募过」= **「已招募」判据的第一候选**；
* `SQ_CrewScript._CustomSetRoleAvaliable()` → `Game.AddToAvailableCrew(actor)`
  （引擎原生函数）—— 招募动作确实写「可用船员池」，faction 成员状态很可能随之变化
  （**待实机探针证实**：把已招募的（如 Vasco）与未招募的对比 A/C/P 位）；
* NPC_ 静态 SNAM 里的 `rank=255` = **int8 的 -1**（= 不自动加入）⇒「静态挂着」不是
  「运行时成员」（这是 16.3「初始都挂着、不能只凭挂着判定」的机制解释）。
