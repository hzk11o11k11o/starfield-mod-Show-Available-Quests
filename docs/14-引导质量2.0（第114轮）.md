## 二、否定性判定：「玩家位置因子」不做（数据说话）

第 47/45 轮的「后续可选」里写着「候选排序引入玩家位置因子」。本轮**核查后决定不做**，
理由按重要性排：

1. **会与第 45 轮的质量分级冲突**：`quality_key = (grade, persistent, order)` —— grade 判的是
   「这个目标是不是正确的接取点」（有名字的 NPC > 可读名落脚点 > 通用名 NPC > 内部名）。
   「按距离最近选」会把精确 NPC 压给「更近的内部标记」（如 `*_DebugMarker`），
   正是第 45 轮玩家反馈修掉的那类问题（「平衡账目」曾被引到 `EnableRef`）。
2. **可得性已经隐含位置优先**：非常驻候选只在「玩家靠近」时才 `LookupByID` 命中 ——
   「第一个可得」本身就把远处候选排除了。跑数据：候选池 1020 条里常驻 372 条，
   绝大多数任务的「多候选同时可得」场景 = 玩家已在目标 cell（此时按顺序取 grade 最优，
   已是最优解）。
3. **需要新的引擎读取（未验证的偏移）**：要算真实距离需读引用坐标（`TESObjectREFR` 的
   `data.location`，commonlibsf 标 0x0C）与玩家坐标；项目纪律「结构体偏移一律不可信」，
   引入即要一轮实机验证 —— 收益（2 的情形下≈0）与风险不成比例。

⇒ 取而代之的是**数据侧的位置精确化**（本轮 A/B/C 三项的实际落地，见下节）：
「让每个候选/兜底都落在正确的位置」比「运行时按距离挑」更直接、可离线验证、零风险。

## 三、实现：两档兜底 + 相关名优先（`tools/esm/gen_guide_targets.py`）

```
find_fallbacks()  （第 47 轮只有一档）
  ① 同 cell 常驻引用（原有）—— 同 cell 内离任一候选目标最近
  ② ★ world 级常驻引用（本轮新增）—— ①找不到时，在候选的 worldspace 里找
     `Top 'WRLD' > WRLD 组 > … > CellPersistent` 的常驻引用，取最近
  两档内部都做「相关名优先」：
     * 任务 EDID 拆词（≥5 字符、去通用词）→ 引用 EDID 含任一关键词 = 相关
     * 相关引用**只有在距离 ≤ 最近距离 + 30 米**时才优先（`_REL_MAX_EXTRA_M`）
       —— 保证「不显著变差」；实测 ≥3 米距离差时仍选最近的那个
```

配套：
- `collect_candidates` 的候选新增内部字段 `world`（与 `pos/cell` 一样，输出 JSON 前剥掉）；
- 兜底候选的 `src` 文案区分两档：`同 cell 常驻兜底（距目标 N 米）` /
  `world 级常驻兜底（距目标 N 米，外景城市）`；
- 生成日志新增一行：`常驻兜底：N/M 条任务找到兜底（同 cell X + world 级 Y）` +
  `（其中 Z 条命中了「任务相关名」优先规则）`。
