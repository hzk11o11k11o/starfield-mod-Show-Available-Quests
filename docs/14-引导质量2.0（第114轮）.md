## 一、数据核查：20 条「无兜底」任务的真相

第 47 轮的 `find_fallbacks` 只做「同 cell 常驻引用」一档，当时 **76 条里 56 条命中、20 条没有**。
本轮先查那 20 条（`tools/esm/_tmp_r114_analyze_no_fallback.py` /
`_tmp_r114_recalc_fb.py` / `_tmp_r114_cell_struct.py` / `_tmp_r114_persist_census.py`）：

| 发现 | 证据 |
| --- | --- |
| 20 条任务的 23 个目标 cell **一条常驻引用都没有** | 逐 cell 统计：如 `NACommercialDistrictStart`（1054 条引用 / 常驻 0）、`GagarinExt02`（10356 / 0）、`SettleRedMile01`（6591 / 0）、`SettleNewHomesteadMainBuilding01`（4175 / 0）… 23/23 全 0 |
| 这不是结构限制 | Starfield.esm 全量普查：**16156 条外景常驻引用**分布在 431 个 cell，其中 base=XMarker 的 1313 条 —— 只是这 23 个「城市外景流式 cell」官方没放 |
| 它们的常驻引用在 **world 层级** | 组链 `Top 'WRLD'(0) > WRLD 组(1, label=world FormID) > … > CellPersistent(8)`，如 world 0x1251B（杰米森）有 1630 条 —— 这正是**第 80 轮外景 NPC 条目兜底**用过的那一套（当时实测「离探员 3.1 m」） |
| 用 world 级兜底的精度足够 | 19/20 条命中，距离 **0.2 ~ 20.4 米**（`_tmp_r114_world_fb3.py`）；只有 `SFBGS001_VKaiZ02`（ShatteredSpace）没拿到 world（见第五节） |

⇒ 结论：**「补常驻 XMarker（改 ESM）」这条路不必走** —— 外景的世界级常驻引用已经
提供了精度相同的兜底（0.2~20 米 vs 自建 marker 的「照抄坐标」，且零 ESM 风险）。

## 二、否定性判定：「玩家位置因子」不做（数据说话）

第 47/45 轮的「后续可选」里写着「候选排序引入玩家位置因子」。本轮**核查后决定不做**，
理由按重要性排：

1. **会与第 45 轮的质量分级冲突**：`quality_key = (grade, persistent, order)` —— grade 判的是
   「这个目标是不是正确的接取点」（有名字的 NPC > 可读名落脚点 > 通用名 NPC > 内部名）。
   「按距离最近选」会把精确 NPC 压给「更近的内部标记」（如 `*_DebugMarker`），
   正是第 45 轮玩家反馈修掉的那类问题（「平衡账目」曾被引到 `EnableRef`）。
2. **可得性已经隐含位置优先**：非常驻候选只在「玩家靠近」时才 `LookupByID` 命中 ——
   「第一个可得」本身就把远处候选排除了。跑数据：候选池 1020 条里常驻 372 条，
   绝大多数任务的「多候选同时可得」场景 = 玩家已在目标 cell（此时按顺序取 grade 最优，
   已是最优解）。
3. **需要新的引擎读取（未验证的偏移）**：要算真实距离需读引用坐标（`TESObjectREFR` 的
   `data.location`，commonlibsf 标 0x0C）与玩家坐标；项目纪律「结构体偏移一律不可信」，
   引入即要一轮实机验证 —— 收益（2 的情形下≈0）与风险不成比例。

⇒ 取而代之的是**数据侧的位置精确化**（本轮 A/B/C 三项的实际落地，见下节）：
「让每个候选/兜底都落在正确的位置」比「运行时按距离挑」更直接、可离线验证、零风险。

## 三、实现：两档兜底 + 相关名优先（`tools/esm/gen_guide_targets.py`）

```
find_fallbacks()  （第 47 轮只有一档）
  ① 同 cell 常驻引用（原有）—— 同 cell 内离任一候选目标最近
  ② ★ world 级常驻引用（本轮新增）—— ①找不到时，在候选的 worldspace 里找
     `Top 'WRLD' > WRLD 组 > … > CellPersistent` 的常驻引用，取最近
  两档内部都做「相关名优先」：
     * 任务 EDID 拆词（≥5 字符、去通用词）→ 引用 EDID 含任一关键词 = 相关
     * 相关引用**只有在距离 ≤ 最近距离 + 30 米**时才优先（`_REL_MAX_EXTRA_M`）
       —— 保证「不显著变差」；实测 ≥3 米距离差时仍选最近的那个
```

配套：
- `collect_candidates` 的候选新增内部字段 `world`（与 `pos/cell` 一样，输出 JSON 前剥掉）；
- 兜底候选的 `src` 文案区分两档：`同 cell 常驻兜底（距目标 N 米）` /
  `world 级常驻兜底（距目标 N 米，外景城市）`；
- 生成日志新增一行：`常驻兜底：N/M 条任务找到兜底（同 cell X + world 级 Y）` +
  `（其中 Z 条命中了「任务相关名」优先规则）`。

## 六、待定 4 条任务的实机确认（4 条 harness 用例）

4 条用例的都遵守同一纪律（verify 有反向检查）：

1. **只读**：不 `quest.reset`、不推 stage（免得「实机确认」反而污染存档状态）；
2. **表外直拼**：`~<master>:0x…`（这 4 条都不在可接任务静态表里）——
   第 110 轮的驱动器能力；
3. 「进入地点触发」型的三条额外做 `teleport` 到接取点引用 —— 观察传送后
   `quest.probe` 的状态词是否变「运行中/已开始」（= 判据②的硬证据）；
4. RL040 用只读探针看 `stageDone(30)`（它的「接取动作」= 击中无线电；
   探针回答「这条线在本存档里有没有被触发过」）。

**判读（跑完看这两处）**：
* `quest.probe` 行的状态词（未开始 / 运行中 / 已开始）—— 现状；
* `teleport` 之后的 probe 行 —— **变了 = 进入地点真的启动了它**；
  没变 ⇒ 还有前置没满足（把 probe 状态抄进 `docs/12` 即可）。
