## 三、第 14 轮：交互与原版对齐（点子项＝切换引导）+ 竖条刷新改按 uID

### 2.1 玩家反馈（第 13 轮部署后）

> 「现在确实可以通过选中让竖条变蓝了，但交互方式与原版相反 —— 原版是点击任务的**子项**，我们却是点击任务的**主标题**。」

### 2.2 原版的交互长什么样（从反编译源码确认）

| 操作 | 原版行为 | 出处 |
| --- | --- | --- |
| 点/回车**主标题**（有子项） | 只做展开 / 收起 | `BSScrollingTree.onEntryPress`：`EntryHasChildren(selectedEntry)` → `ShowEntryChildren` |
| 回车**子项** | 切换追踪（竖条亮 / 灭） | `MissionMenu.onMissionListItemActivated` 的门槛 `CanTrackOrUntrack = !IsMission(entry)` —— 只有非主标题才继续往下走 |
| 按 X（SET COURSE） | 对选中的目标设定航线 | `OnPlotCourseEvent` |

第 13 轮的判定插在函数最前面，且只认「主标题」（`SaqIsOurEntry` 只看 `bSaqAvailable`，当时只有主标题带这个标记）
⇒ 点主标题就切换引导，与原版正好相反。

### 2.3 本轮的修改

| 改动 | 说明 |
| --- | --- |
| 子项也带 `bSaqAvailable` | `SaqBuildObjective` 加标记 ⇒ `SaqIsOurEntry()` 对主标题与子项都成立（按钮状态、X 键判定一致） |
| `onMissionListItemActivated` 分流 | 我们的**主标题** → 直接 return（展开/收起交给 `BSScrollingTree.onEntryPress`）；我们的**子项** → `SaqToggleGuide()` |
| X 键不变 | 选中主标题或子项按 X（SET COURSE）= 切换引导（主标题等于原版「导航到目标」的入口） |
| 竖条刷新改按 uID | 新增 `MissionsList.SAQ_RefreshQuestRow(uID)`：在当前显示列表里按 uID 找行（含已展开的子项）就地重渲染 |
| 子项能找到父任务 | `GetParentMissionData()` 增加 AvailableQuests 兜底 ⇒ 选中子项时右侧详情面板显示父任务内容 |
| 描述文案更新 | 「展开后选中目标（或按 X 键 / SET COURSE）即可引导到接取地点」 |

**为什么要新增 `SAQ_RefreshQuestRow`**：第 13 轮按「数据下标」调 `BSScrollingList.UpdateEntry(QuestData.length + i)`，
但 ① 列表的**显示下标 ≠ 数据下标**（`InitializeEntries` 会把已完成 / misc 条目挪位，展开时子项还会插进来）；
② `BSScrollingList` 根本没有 `UpdateEntry` 这个接口（只有 `BSTabbedSelection` 有一个 protected 的同名方法）——
那次调用实际每次都会抛 `Error #1006` 并被 `try` 吞掉，竖条能不能亮全看列表有没有被别的原因重建。
新接口在列表内部实现（那里是唯一能访问 `entryList` / `UpdateEntryClip` 的地方），按 uID 找行，行为确定。

### 2.4 待验证（本轮部署后）

* 展开一条可接任务 → 选中子项「前往接取地点」按回车 / 鼠标点击：**该任务主标题左侧竖条变蓝**；再操作一次复位；
* 选中**主标题**按回车 / 点击：只展开 / 收起，竖条**不再**变化；
* X 键：主标题 / 子项选中时都能切换引导；日志 `guide=<序号>|<FormID>|已设为引导:<任务名>` 里应是**任务名**（子项触发时不再是「前往接取地点」）。

## 四、第 15 轮：提示文案里不存在的「X 键」——键名改为按控制映射动态取

### 3.1 玩家反馈（第 14 轮部署后）

> 「整体功能看上去一切正常，只不过那个『按 X 键』的提示有点问题，游戏内没有这样的交互。」

### 3.2 根因：`XButton` 是**手柄按钮**的内部事件名，不是键盘 X 键

| 事实 | 证据 |
| --- | --- |
| `SET COURSE` 按钮绑定的事件名是 `"XButton"` | `PopulateButtonBar()`：`new UserEventData("XButton", this.OnPlotCourseEvent)` |
| 键盘下该事件映射到 **R** | 玩家截图底部按钮栏 =「设定航线 R」；按钮栏键名与文案同源（`KeyHelper.GetButtonNameForEvent`） |
| 第 12~14 轮把 `XButton` 直译成「X 键」 | 详情面板描述文案「…（或按 X 键 / SET COURSE）…」⇒ 提示了一个游戏里不存在的键 |

⇒ **凡是提示键名的地方都不能写死**，要用 `KeyHelper.GetButtonNameForEvent(事件名, "")`
取当前设备（键盘 / 手柄）的实际键名 —— 这与底部按钮栏显示的是同一个值。

### 3.3 本次改动

| 改动 | 说明 |
| --- | --- |
| `SaqDescriptionText()` 键名动态取 | 有键名 ⇒「…或按 R（设定航线）…」（手柄则显示手柄键名）；`try/catch` + 空值兜底 ⇒「…或使用底部的『设定航线』…」 |
| 相关注释一并更正 | 文件头 / `onMissionSelectionChange` / `OnPlotCourseEvent` 三处注释里的「X 键」改为「SET COURSE（键盘 R / 手柄 X）」 |
| `docs/05` 同步更正 | 第六节新增「提示键名不要写死」一条（事件名 = 手柄按钮名，键盘映射不同） |
| 只改普通版源码 | `ui/missionmenu_lrg` 由 `make_lrg_source.py` 生成；`build-saq.ps1 -SkipTable -SkipPlugin -SkipPapyrus` 重编译两个 SWF 并部署 |

### 3.4 验证（已做）

解压 SWF 常量池（`CWS` → `zlib`）后按 UTF-8 检索，**四处产物一致**：
工作区 `missionmenu.swf` / `missionmenu_lrg.swf` + MO2 部署副本：

```
新文案（"或按"/"设定航线"）: True    SET COURSE: True    旧文案（"按 X 键"）: False
```

游戏内判据：选中一条可接任务 → 右侧描述应为「…展开后选中目标，或按 R（设定航线）…」；
按 R（即底部「设定航线」）应能切换引导（与第 14 轮一致）。

## 五、第 13 轮：HUD 目标文本改固定文案 + 条目的「追踪中」竖条

### 2.1 玩家反馈（第 12 轮部署后）

1. HUD 里任务名已显示（「可接任务」），但目标文本那一行仍是 `[...]`
2. 条目仍无法像原版任务那样「选中」——原版选中/追踪时列表左侧的竖条会变蓝，我们的恒为灰

### 2.2 查证与修复

**目标文本为什么还是 `[...]`**：第 12 轮已补 NUL（所以 FULL 显示正常了），但
`<Alias=SAQ_GuideTarget>` 依旧不被替换。两条实证：

* 扫遍本机所有**非本地化**第三方 ESM（QUST 内联 NNAM 共 9 条）——**没有一条**使用 `<Alias=...>`
  （`morelore_mantislegacy.esm` 用的是纯固定文案，如「前往五帝座一I-b的祈祷者踪迹」）；
* 原版的 `<Alias=...>` **全部在本地化 strings 表**里（记录里只存字符串 ID），
  例如 `0x0002D33A = "Collect the bounty on the <Alias=PrimaryRef> at the <Alias=TargetLocation>"`。

⇒ **内联文本的别名替换没有先例**，改成固定文案 `"前往接取地点"`。
「去找谁 / 去哪」由引导的蓝点 + 扫描仪路径线承担（`QSTA` 仍指向别名 0，不动）。

**竖条不变蓝**：原版这条竖条是 `MissionVisuals_mc.TrackIndicator_mc`，由条目数据的 `bActive`
驱动（`MissionsListEntry.SetMissionTracked`：`true` → "Active" 帧、`false` → "Inactive"）。
我们的条目 `bActive` 恒为 false ⇒ 恒灰。**修复**：把「引导中」映射到 `bActive`——

* `SaqToggleGuide` 切换后调用 `SaqApplyTrackedMarker(旧 uID, 新 uID)`；
* 就地刷新用 `BSScrollingList.UpdateEntry(下标)`（只重渲染指定行，不动滚动/展开状态；
  下标 = `QuestData.length + AvailableQuests 里的下标`，因为列表数据 = `BuildMergedList()`）；
* `SaqBuildEntry` 里 `bActive` 也按当前引导任务初始化 ⇒ 列表重建（SaqRefresh）后不丢状态。

### 2.2 逐条查证与修复

| --- | --- | --- |
| HUD 显示 `[...]` | 代理任务的目标文本 `NNAM` 没写 NUL 终止符（len=23 = 恰好 23 个可见字符）。对照两个非本地化第三方 ESM：`StarfieldAlwaysScan.esm` 的 FULL len=12（"Always Scan" 11+NUL）、`morelore_mantislegacy.esm` 的 NNAM 全部是「文本+1」 | `patch_saq_esm.py`：`NNAM` 末尾补 `\x00`（len 24） |
| HUD/日志里任务没名字 | 代理任务的 QUST 没有 FULL（第 11 轮日志 `qdata[10]` 里 `f000800:` 那条空名字就是它） | 加 `FULL = "可接任务"`（UTF-8 + NUL；FULL 移出白名单 ⇒ 每次幂等重写） |
| 看不到任务阶段 | 我们的条目 `aObjectives` 是空数组；原版展开子条目 = `aObjectives`（`MissionsList.GetChildrenOfEntry`） | AS3：每条附一条 objective（「前往接取地点」）+ 右侧描述（「…按 X 键可引导…」） |

### 2.3 卡顿定位（第 11 轮埋点拿到了数据）

```
[06:52:18.988] 推送失败（第 1 次，完整诊断）：… | 耗时 109 ms
[06:52:23.309] 主线程停顿：距上次 Tick 3922 ms
[06:52:27.220] 推送失败（重试）：Movie/ASMovieRoot 解析失败：… | 耗时 3921 ms
[06:52:35.078] 主线程停顿：距上次 Tick 11781 ms（= 3 × 3.92 s）
[06:52:47.205] 推送成功：… | 耗时 235 ms
```

* 失败路径固定 ~3.9 秒、成功路径 235 ms ⇒ 时间花在 `ResolveMovieChain` 的失败解析上。
* 该路径的热点是 `FindAsRootSlot`：2048 步 × 2 次 `ReadPtr`，而每步 `ReadPtr` 都会
  `IsMapped`（`VirtualQuery` 内核调用）—— 正常 ~μs 级，但在游戏进程里（VAD 树大 +
  与引擎的内存操作抢锁）明显更贵，4000+ 次累计成秒级。
* **修复**：`SafeRead` 去掉 `IsMapped` 前置检查，改**纯 `__try` 保护**（有效指针零开销，
  坏指针才走异常）；`FindAsRootSlot` 开头的预检同样去掉。
* 另加分段计时（表解析 / Movie 链 / 失败诊断）写进 detail，下次日志一眼可辨。

### 2.4 待验证（第 12 轮部署后）

## 七、第 11 轮：修掉「全数到期」被误过滤（核心）+ 打开菜单卡顿的诊断埋点

### 2.1 玩家报告与查证过程（证据链）

玩家在 GalBank 里报告：**「和 NPC 对话就能接到『全数到期』，但可接任务列表里没有这条」**。

查证（第 11 轮新增的诊断日志直接给出答案）：

1. `全数到期` = `RAD05` / FormID **`0x002AD3D5`**（GalBank 的 Landry Hollifeld 提供的**可重复**辐射任务，
   4 变体、可立即重复接取），在静态表里（第 181 条附近）。
2. 第 11 轮把「运行时隐藏」名单从「前 5 条样本」改成**完整列出**后，日志首批命中：
   ```
   隐藏: ... 全数到期[0x002AD3D5 运行中 flags=0x8001] ...
   ```
   ⇒ 它被 `started`（TESQuest flags bit0）挡掉了。
3. AS3 侧新增的 `qdata[...]`（玩家任务日志名单）显示：
   ```
   qdata[9]=[2c9c97:重返职场,2c5401:超越极限,114cd:老住区,a47b8:梦想家园,
             270718:新亚特兰蒂斯城有棵树,fd000cf2:追踪者联盟,50179a3:壳带中的回响,0:活动,3448:一小步]
   ```
   **没有 0x2ad3d5** ⇒ 玩家根本没接过它。
4. 30 条「已开始」里，只有 3 条（重返职场/超越极限/新亚特兰蒂斯城有棵树）在玩家日志里；
   **其余 27 条都是「引擎提前置成 running、玩家还没接」的任务**。

**结论：「已开始」≠「已接取」**。引擎会把「玩家仍能从 NPC 接到」的任务提前启动
（RAD05 这类可重复辐射任务的对话链/事件准备），拿它当过滤判据必然误伤。

### 2.2 修复（判据分工重划）

| 层 | 新判据 | 说明 |
| --- | --- | --- |
| C++（`CollectAvailableQuests`） | **只挡「已完成」**（`state.completed`） | 做过的任务不该再出现在「可接」里 |
| C++（`AutoClearGuideIfAccepted`） | 同上（只看 completed） | 原来 started 也触发，会让 RAD05 的引导「刚设上就被取消」 |
| AS3（`FilterKnownQuests`，原有逻辑） | **玩家任务日志（QuestData）里有该 uID ⇒ 不显示** | 「已接取」的唯一权威数据 |

预期效果：`202 - 1(已完成：食宿) - 3(玩家日志里已有的) ≈ 198 条`，
**「全数到期」会出现在列表里**。

## 九、第 10 轮：任务引导（实现见 `docs/05`）

需求里的「能调用游戏的任务引导系统正常引导到接取任务的地点」这轮落地了整条链路：

```
AS3 选中条目按 Enter/X → SAQ_PeekGuide() "<序号>|<任务FormID>"
  → DLL 轮询（100ms）→ 静态表取「引导目标引用」→ 写 GLOB（SAQ_GuideTargetRef + GuideState=0）
  → SAQ_Main.psc 0.5s 轮询/菜单关闭 → GetAlias(0).ForceRefTo(目标) + SetObjectiveDisplayed(10)
                                    + SetActive(true)
  → 引擎画任务标记（蓝点）+ 扫描仪路径线
```

三个关键决策（每一个都留了证据）：

| 决策 | 为什么 |
| --- | --- |
| 引导目标 = **任务发布者的放置引用 / 任务自己的落脚引用**（离线算，83% 覆盖） | 引擎只认「世界里的一个引用」；发布者就是「去哪里接」的答案。地点地图标记（`LCTN.MNAM`）只有 7% 的任务有，做兜底 |
| **优先常驻（persistent）引用** | 非常驻引用要等格子加载，玩家在远方时 `Game.GetForm` 拿不到 ⇒ 引导失败。168 条里常驻 100 条 |
| 通道用 **GLOB**，并靠脚本写的**魔数 7777** 反查自己插件的加载序号 | SFSE 没有「C++ 直接给 Papyrus 发事件」的接口；FormID 的高 8 位运行期才知道，不能写死 |

顺带把**身份锚点**变成了证据链：日志里 `通知=7777` ⇒ ESM 已加载、代理任务在跑、脚本活着；

### 玩家反馈（第 20 轮部署后的实测，10:23~10:25 会话）

### 日志证据：事故从「第一个 DLC 目标」开始

```
[10:23:57.501] 引导请求：星海萨普之旅（0x0021710B）→ 引用 0x0021C69A（新家园）    ← 成功
[10:23:59.906] 引导请求：取消｜…                                                ← 成功
[10:24:04.281] 引导请求：阿基拉城任务（0x002A4401）→ 引用 0x0012253A             ← 成功
[10:24:11.501] 引导请求：同情生者（0x010D5E84）→ 引用 0x0107BDB2（瓦鲁贮藏所）   ← 成功（首个 DLC 目标）
[10:24:11.940] [W] 引导请求：取消失败｜拒绝写入：SAQ_GuideTargetRef 读出来是 17284530（不像 FormID）
[10:24:17.626] [W] 引导请求：阿基拉城任务（0x002A4401）写 ESM 通道失败｜（同上）    ← 之后全部失败
…（结果码 2 一直刷到 10:25:46 关菜单）…
```

`0x0107BDB2` = 17,284,530 —— **第一个超过 0xFFFFFF 的引导目标**（DLC 的引用），事故起点。

### 根因（都在 `SAQ_Guide.cpp::SetGuideTarget`）

| # | 错 | 后果 |
| --- | --- | --- |
| 1 | **自检上限写成 `16777215`（0xFFFFFF）** —— 那是「低 24 位」的上限，而 target 里存的是**完整 FormID** | 通道里一旦存过 DLC 目标（> 0xFFFFFF），**之后每次写入都被这个自检拒绝**（结果码 2）⇒「点亮瞬间取消 / 全都点不亮」 |
| 2 | GLOB 是 float（尾数 24 位），完整 FormID > 2^24 后**奇数不可精确表示**（±1） | 轻则 `GetForm` 取不到（状态 2），重则**指向相邻的另一条记录 = 错误的引导目标**（DLC 目标约一半是奇数） |

### 修法

| 改动 | 说明 |
| --- | --- |
| 目标 FormID 拆两个 GLOB | `SAQ_GuideTargetRef`（0x801）改存**低 24 位**，新增 `SAQ_GuidePrefix`（0x805）存**高 8 位** —— 两个分量都在 float 精确区（脚本 `GuidePrefix != None` 自动兼容旧通道） |
| VMAD | `build_saq.pas` 追加 `GuidePrefix` 属性绑定（VMAD 96 → 119 B），**重跑了一次 `-RebuildEsm`**；FormID 0x800~0x805 不变（追加在末尾） |
| 自检修正 | 有拆分 GLOB 时按分量检查（低 24 位 ≤ 0xFFFFFF / 高位 ≤ 0xFF）；旧 ESM 用完整 FormID 上限 0xFEFFFFFF |
| 遗留值兼容 | 修复前存档里残留的完整 FormID（prefix 还是初值 0）由 `CombineTargetFormID` 按旧语义识别，并在下一次写入时被新语义覆盖（不会卡死） |
| 日志 | 通道摘要 `目标=0x{:08X}`（拼好的完整值）；写入详情 `写入 SAQ_GuideTargetRef=0x… + SAQ_GuidePrefix=…（完整 0x…）` |

### 验证（已做）

* ESM：xEdit 重建 + patch 幂等；GLOB = 0x801..0x805、QUST formid=02000800（未变）；

## 一·补九、第 24 轮：无引导目标的 52 条 —— 归因分析（结论：不补「猜的导航」）

玩家要求：**先分析清楚「为什么有些任务无法导航」，再决定要不要补** —— 不要为了导航而
