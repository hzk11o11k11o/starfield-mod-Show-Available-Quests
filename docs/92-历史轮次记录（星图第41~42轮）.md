## 十五、★★ 第 41 轮：星图链路两个确定性 bug —— 注册名错 + 特征字节抄反


**这一轮没有玩家反馈新内容，来源是「日志 × 离线复查」的主动排查**（第 40 轮判据待实测时
先做了引擎侧核对，一次挖出两个「让前四轮结论全偏」的 bug）。

### 15.1 ★ Bug 1：星图的注册名是 `GalaxyStarMapMenu`，不是 `MapMenu`

第 37 轮把「星图菜单名」定成了菜单名表（`.rdata 0x4D7E010`）里的 `MapMenu`，
DLL 的 `CheckStarMapOpened` / `OpenMenusSummary` 从那时起就用它做判据。

离线复核（可复现）推翻了它：引擎自己打开星图的两个函数
`ShowGalaxyStarMapMenu`（0x2010170）与 `ShowGalaxyStarMapMenuAndPlotToLocation`（0x2010210）
都先调 `0x253CFA0` 取菜单名 —— 那是一个**惰性初始化的静态 BSFixedString**：

```
0253CFE7  lea rdx, [rip + 0x2759352]   ; -> .rdata 0x4C96340  "GalaxyStarMapMenu"
0253CFF8  call 0x28cba80               ; 构造静态 BSFixedString（存 0x82FA638）
...
0253D017  mov rax, rbx                 ; 返回它
```

而 0x2010210 随后就用它发 UI 消息：

```
020102D1  call 0xc83790   ; UIMessageQueue::AddMessage(queue, "GalaxyStarMapMenu", kShow, 描述符, 载荷)
```

⇒ **星图的注册名是 `GalaxyStarMapMenu`**（`MapMenu` 是菜单名表里**另一个**菜单的名字）。
⇒ 第 37~40 轮所有「星图没有打开 / 12 秒内没有出现」的判定**全部是假阴性**：星图其实
每次都开了 —— 玩家反馈「R 键可以打开星图」（第 40 轮）、「有时候打开了星图」（第 38 轮）
才是真相；第 40 轮「调用太早被引擎丢掉」的推理前提不成立（延时与重试本身无害，保留）。

复现：`python tools/re/dis_range.py 0x253cfa0 0x253d060` / `0x2010210 0x20102c8`。

### 15.2 ★ Bug 2：节点解析器的特征字节抄反

第 40 轮给 `0xAC2AB0`（地点 → 星图节点解析器）写的函数头特征是
`4C 89 1C 24 49 89 5B 20`。实际字节是 `4C 8B DC 49 89 5B 20`：
`mov r11, rsp` 的机器码是 **`4C 8B DC`**（`4C 89 1C 24` 是 `mov [rsp], r11` —— 方向反了），
后面跟 `mov [r11+0x20], rbx`（`49 89 5B 20`）。

⇒ 运行时特征校验**永远失败**，日志全是「节点解析器不可用：游戏版本特征不符」，
「指错星球」的唯一定性判据一直是瘸的（17:18 会话的 4 行诊断全被这一条堵死）。
第 41 轮改为 `{4C 8B DC 49 89 5B 20 55}`（末尾多带一个 `push rbp` 增强特征）。

复现：`python tools/re/dis_range.py 0xac2ab0 0xac2ae0`。

### 15.4 判据（下次进游戏，一次会话看完）

1. **核心**：选一条有导航目标的可接任务按 R ⇒
   `星图：已打开（GalaxyStarMapMenu 在屏幕上，R 后约 N 秒，第 1 次尝试）`（N 应 ≈ 1.5~2.5）；
2. **`星图诊断（R 请求）` 现在应有真实数据**（不再有「特征不符」）：地点链每层的
   `节点=0x…` —— 哪一层不为 0 = 星图该用那一层的地点；全 0 = 引擎不认这条链
   （下一步走 `StarMap::SetCourseTo*` 消息族）；
3. 玩家眼睛：星图聚焦到**接取地点所在行星**、有航线；若仍指错，把 `采用地点=` 与
   `星图诊断` 的地点链一起反馈（两行合起来直接区分「节点没命中」与「命中但不按它定位」）；
4. 回归：Enter 子项只引导（不关菜单、不开星图）；同一条再按 R = 保持引导 + 再开星图
   （此时应看到又一次 `星图：已打开`）；菜单里停 20 秒+ 无 `引导未生效`。

## 十六、★★ 第 42 轮：R 键「导航目标不是我悬停的那条」—— 证据补齐 + 两条会改掉目的地的缺陷


**玩家反馈**：「R 键的导航结果似乎不太稳定，有时候导航的目标似乎不是鼠标悬停的任务的目标」。

### 16.1 先把「界面用的是哪一行」变成日志里的硬证据

此前（第 10~41 轮）日志里只有 C++ 解析出来的任务（`引导请求：<任务名>（0x…）`），
**没有任何一行**记录「按键那一刻界面选的是哪一行」⇒ 「界面选错行」与「界面选对了、后面某一段错」
这两种可能一直分不开（第 38/39/40 轮的 R 反馈都因此无法定性）。

本轮补上（AS3 → 报告 → DLL 抄录）：

```
AS3  MissionMenu.as
  OnPlotCourseEvent（R / 手柄 X）  ⇒ SaqLastPressNote = "R@"      + SaqEntryTag(选中条目)
  onMissionListItemActivated（Enter）⇒ SaqLastPressNote = "E@"      + …（原版条目写 "E(原版)@"）
  onMissionSelectionChange         ⇒ SaqLastSelNote  = "idx=<下标>:" + …（鼠标悬停会更新它）
  SaqEntryTag(entry) = "0x<uID 十六进制>@<显示名>"（名字里可能有空格 ⇒ 报告里用 press=[…] 包起来）
  SAQ_Report ⇒ … proxy=0x… press=[…] sel=[…] qdata[…] drop[…]

DLL  SAQ.cpp
  As3PressNote() / ExtractBracketField()：现场读一次报告，抄出 press/sel（找不到给 "?"）
  `引导请求：<任务名>（0x…）→ 引用 0x…（地点）｜…｜星图=是｜press=R@0x351a@平衡账目 sel=idx=137:0x351a@平衡账目`
```

判读方式（一次会话即可定性）：

| 日志形态 | 结论 |
| --- | --- |
| `press` 的 uID ≠ 引导请求的 uID | **界面按键时用的行本来就不是它**（选中项与悬停不一致），锅在 AS3 侧 |
| `press` ≠ `sel`（uID 不同） | 按键那一刻「悬停的行」与「列表选中项」已经脱钩（列表重建/焦点问题），同一类锅 |
| `press` = 请求的任务 | 界面选对了 ⇒ 去看后面的通道（脚本/星图）那一段 |

### 16.2 缺陷 ①：DLL 星图重试抢在脚本前面换地点候选（第 40 轮遗留）

第 40 轮的重试从**请求时刻**起算 2.5 秒（`kStarMapRetryMs`）就把 `SAQ_GuideState` 从 5 改成 6、7
（换地点候选）。而脚本那一半的时序是：

```
菜单关闭事件 → ApplyGuide：应用引导（写状态 1）
             → StartTimer(StarMapDelay = 1.5 s, StarMapTimerID)   ← 玩家按 R 后约 1.5~2.5 s 才调原生函数
             → OnTimer：Game.ShowGalaxyStarMapMenuAndPlotToLocation(地点)
```

⇒ 2.5 秒的重试正好落在脚本自己的窗口里，两种坏结果（都表现为「目的地变了 / 不稳定」）：

1. **脚本还没跑到就换候选**：候选 5（行星自己的地点，第 40 轮的新默认）**从未被试过**，
   日志却写「第 2 次尝试」；
2. **星图刚开就被重画**：按候选 5 打开后又被候选 6/7 重画一次（航线/焦点跳变）。

**修法（`CheckStarMapOpened`）**：重试的前置条件从「距请求多少秒」改成
**「先看到脚本应用（`GuideState == 1`），从那一刻起再等 3 秒（`kStarMapRetryAfterAppliedMs`）」**：
脚本的状态 1 一定是它处理了**本次**请求后写的（DLL 在 `SetGuideTarget` 里刚把状态写成 5/6/7），
所以不存在「读到上一次的 1」的歧义；菜单开着时照旧推迟重试（游戏暂停时脚本跑不到）。
新日志：`星图：脚本已应用这次引导（状态=1）…` / 重试行写 `脚本已应用 N 秒仍未出现 ⇒ …地点候选随之切换`。

> 为什么保留换候选：它仍是「引擎不认这个地点链」的兜底（1.5 秒后星图仍未出现 = 第一次调用真的
> 没生效）；只是不再允许它抢在脚本自己那一次尝试前面。

### 16.3 缺陷 ②：脚本的星图延时待办在「换了引导」后没作废（第 37 轮起）

`StarMapPendingRef` / `StarMapPendingMode` 只在「新的星图请求」时被覆盖。延时窗口（1.5 s）里
玩家完全可能去引导**别的任务**——Enter 点「前往接取地点」、取消引导、或接取后自动取消都没带星图意图
⇒ 待办仍指着**上一条**任务，定时器到点就把**旧任务的航线**开出来：玩家看到星图指的地方与
自己刚选的条目对不上（正是本条反馈）。

**修法（脚本，两处）**：

```
ApplyGuide()
  ├─ 任何一次新请求（状态 0/5/6/7）先作废待办：StarMapPendingRef = None / StarMapPendingFormID = 0
  └─ starMapWanted 分支再装上：目标引用 + StarMapPendingFormID = targetFormID + StartTimer(1.5)

OnTimer(StarMapTimerID)
  ├─ 取出待办并清空（避免重入）
  ├─ ★ 过期校验：StarMapPendingFormID 必须 == CurrentGuideTargetFormID()（通道里的当前目标）
  │    不等 ⇒ Debug.Trace("[SAQ] 星图请求已过期：待办目标 X ≠ 当前目标 Y（引导已换/已取消）—— 跳过打开星图")
  └─ OpenStarMapFor(待办引用, 候选号)
```

`CurrentGuideTargetFormID()`（低 24 位 + 高 8 位拼装）与 `ApplyGuide` 共用同一套逻辑，
避免两处拼法漂移。取消引导（目标 0）同样会被这一步挡住（0 ≠ 待办 FormID）。

### 16.4 顺手加固：`OnPlotCourseEvent` 的空选中

`OnPlotCourseEvent` 原来直接 `MissionsListEntry.IsMission(this.MissionsList_mc.selectedEntry)`；
`selectedEntry` 为空时（悬停到分隔行 `{"bIsDivider":true}`、或该下标还没渲染出来）
`IsMission` 会在 `param1.hasOwnProperty` 上抛异常，异常冒到按钮栏被吞掉 —— 玩家看到的是
**「按 R 没反应」**（另一种「不稳定」）。现在：按键那一刻取一次 `selectedEntry`，
为空直接返回；后续「我们的条目」与原版分支都用这同一个对象（不再两次读 `selectedEntry`，
避免列表在两次读之间被重建换成别的行）。

### 16.6 判据（下次进游戏）

1. 按 R ⇒ `引导请求：…｜界面按键行 press=R@0x…@… sel=idx=N:0x…@…`：**press 的 uID 与请求的任务必须一致**；
   若不一致（或 press 与 sel 不一致）⇒ 界面侧真错行，日志直接留证（本轮新增的判据）；
2. 正常路径：`星图：脚本已应用这次引导（状态=1）…` → `星图：已打开（…第 1 次尝试）`；
   **不应**再出现第 2/3 次尝试（出现即说明第一次调用真的没生效，重试是正当的）；
3. 换任务场景：R（A）→ 星图 → 关掉 → 回菜单 Enter 引导 B ⇒ 蓝点跟 B；
   Papyrus 若出现 `[SAQ] 星图请求已过期` = 16.3 的保护生效（不再冒出 A 的航线）；
4. 回归：Enter 只引导；同一条再按 R = 保持引导 + 再开星图。
